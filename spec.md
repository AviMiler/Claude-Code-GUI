# Spec — Claude Code GUI
_Created 2026-10-27 from what shipped (there was no spec before). Background: ARCHITECTURE.md, AGENT_CONTEXT.md, PROJECT_MAP.md._

Requirements the user confirmed as permanent. Each new permanent feature gets a section here.

## Platform constraints
- Zero npm dependencies; plain JavaScript, ES modules, no build step.
- Runs on a closed (offline) Windows machine, single user, served on http://127.0.0.1:3737. No external files, fonts, sounds or CDNs.
- Hebrew, right-to-left UI; light and dark theme.
- The UI follows the latest Claude Code Desktop Code tab (reference: code.claude.com/docs/en/desktop) as closely as possible; labels are in Hebrew (confirmed 2026-10-27, for the whole Desktop-parity batch).
- Code is separated by feature: a folder per topic (for example `public/js/panes/`, `lib/git/`), no spaghetti between features (confirmed 2026-10-27, code-standards rule 1).

## Notifications (confirmed permanent, 2026-10-27)
The user chooses what to be told about. Frontend only, no server changes.
- Channels (each on/off): desktop notification (browser Notification API; click focuses the tab and opens that session), sound (generated with WebAudio, no audio files; volume setting; rising tone = done, double = waiting, falling = error), tab-title count.
- Events (each on/off): turn finished, waiting for the user's approval (permission, AskUserQuestion, plan card), error (crash, failed start, or a result with isError). A turn the user stopped notifies nothing. A turn held open for a mid-turn correction notifies once, when it really ends (see "Mid-turn correction").
- When: "away" (default: tab hidden or unfocused, or the session is not on screen) or "always". A session shown in the main pane or in the split-view pane counts as on screen (no notification, no unread mark). An archived session never notifies and is never marked unread (see "Archived sessions").
- Tab title shows "(N)" = sessions waiting for approval plus sessions finished and unread (archived sessions are not counted); this replaced the earlier waiting-only count, and can be turned off.
- Settings are per browser (localStorage `claude-gui.notifications`) and edited in the settings modal, panel "התראות" (also a bell button in the sidebar footer). The panel has a test button and shows/requests the desktop permission.
- Defaults: desktop off, sound off, title on, volume 60, all three events on, when = away.
- Code: `public/js/notify.js`, `public/js/page-status.js`, `public/js/panels/panel-notifications.js`; triggers in `public/js/events.js`.

## /btw side questions (confirmed permanent, 2026-10-27)
The user can ask Claude a quick question about the current conversation without interrupting the running turn and without adding to the conversation (like Claude Code's `/btw`). It calls the model, so it costs tokens.
- `/btw <question>` works while a turn runs (it runs at once, it is not queued). `/btw` with no question inserts "/btw " in the composer. It needs an open session; on the welcome page a toast says to open one.
- A card "שאלת צד" above the composer shows the question, a loader, then the answer as Markdown, a follow-up input (the earlier questions and answers of the card are sent as history) and a close button (Esc closes it and does not stop the turn). Selecting another session closes it.
- Not added to the thread, not in the queue, not persisted (history lives only in the open card), no notifications.
- Server: `POST /api/sessions/:id/side-question` `{ question, history }` -> CLI control request `side_question` (starts the session's CLI if needed, 10 minute timeout because the local model can be slow). Limits: question not empty and up to 4000 characters, history up to 20 entries. Kept out of the generic no-token `/control` whitelist on purpose.
- A Claude Code version without `side_question` (2.1.246 is untested) shows a neutral "not available in this version" note (HTTP 501), not an error.
- Code: `lib/side-questions.js`, `public/js/side-question.js`; wiring in `lib/api-routes.js`, `public/js/actions.js`, `command-runner.js`, `commands-data.js`, `app.js`.

## Background tasks (confirmed permanent, 2026-10-27)
The user sees and controls what Claude runs in the background (shell commands, subagents, Monitor) in the session, like Claude Code's `/tasks`.
- Panel "משימות רקע" (settings modal, group session) lists the session's tasks: description, type, status badge (running, completed, failed, stopped, killed), duration, tokens, tool uses, last tool, summary. It updates live. Actions: stop (a running task) and show output (tail of a shell/Monitor task's output). `/tasks` and `/bashes` open it.
- A topbar chip "N ברקע" shows while tasks run and opens the panel. The existing thread notices for task start and finish stay.
- Tasks are kept in memory only, per session, and are never persisted: they live inside the CLI process. When that process ends (crash, kill, idle shutdown, server restart) its running tasks become "killed" with the summary "התהליך של Claude Code נסגר". At most 50 tasks per session (finished ones are dropped first).
- A CLI process is NOT retired by the idle timeout (`idleMinutes`) while it has running background tasks; the timer is re-armed when the last one ends.
- Archiving a session closes its CLI process, so its running tasks become "killed" like on any other exit; the GUI asks first when tasks are running (see "Archived sessions").
- Stop and output use the CLI's `stop_task` / `get_task_output` control requests (no model turn, no tokens), in the generic `/control` whitelist (stop as a write, output as a read).
- A Claude Code version without these events or requests (2.1.246 is untested) shows a neutral "not available in this version" note, not an error.
- Server: SSE `{type:'tasks', sessionId, tasks}`; tasks are also in the session meta. Code: `lib/task-tracker.js`, `readTaskEvent` in `lib/event-translator.js`, hooks in `lib/session-runtime.js` and `lib/session-events.js`, `public/js/panels/panel-tasks.js`, chip in `public/js/chrome.js`, `events.js`.

## Full-text session search (confirmed permanent, 2026-10-27)
The sidebar search ("חיפוש סשנים") finds sessions by the text of their conversations, not only by name and folder. Frontend only, no server changes: the browser already holds every session's items.
- Matches the session name and folder (as before; for a session in its own worktree the folder is the project folder it was opened from, and the worktree's branch also matches, see "Worktree per session") and the text of messages: user messages, Claude's answers (including nested subagent text) and shell commands (`input.command` of tool items). Not searched: thinking, tool results, notices, command output. `/btw` answers are never in the items, so they are not searchable.
- Case-insensitive and ignores Hebrew points (niqqud). Runs on input with a 150 ms debounce. Only the newest 3000 items of each session are scanned; the match count per session is capped at 99 (shown "99+").
- A session that matches by content shows under its row a 2-line snippet around the first match with the match marked, and "· N התאמות". Nothing found: "אין סשנים או הודעות תואמים". Enter in the search box opens the first result. The search covers the list shown: the sessions, or the archive while it is shown (see "Archived sessions").
- Opening a result opens the session with a sticky bar at the top of the thread: "k מתוך N", previous/next (▲ ▼), close. The matching messages are outlined and the current one is scrolled to; a match inside a collapsed tool group or tool row opens it first (see "Transcript view modes"). Enter / Shift+Enter / Esc work while the focus is in the bar. Selecting another session clears the bar.
- Code: `public/js/session-search.js` (pure search), `public/js/search-hits.js` (bar and highlights; opens a hit's collapsed group or row through `transcript/reveal.js`), `sidebar.js` (results), `thread.js` (`data-item-index` on every item node), `events.js`, `app.js`, `css/layout.css`.

## Sidebar: pinned sessions and grouping by project (confirmed permanent, 2026-10-27)
The user keeps important sessions on top and can view the session list by date or by project folder.
- Pin: a boolean `pinned` on the session, saved in `data/sessions.json` and changed through `PATCH /api/sessions/:id` (non-boolean values are ignored). It is not a CLI setting: pinning never restarts or touches the CLI process, and does not change the session's recency. A fork does NOT inherit `pinned`. Archiving a session unpins it, and a pin request for an archived session is ignored (see "Archived sessions").
- Pin/unpin from a pin button on the session row (shown on hover, always visible when pinned), from the row's "⋯" / right-click menu ("הצמדה" / "ביטול הצמדה", see "Context menus for sessions and file paths") and from the topbar "עוד" menu ("הצמדה למעלה בסרגל" / "ביטול הצמדה").
- Pinned sessions show first, in a group "מוצמדים", and ONLY there (not again in their date or folder group). In the pinned group the folder line under the name is shown (for a worktree session followed by its branch, "folder · branch").
- A switch at the top of the sidebar chooses the grouping: "לפי תאריך" (default: היום / אתמול / 7 ימים ...) or "לפי פרויקט" (one group per project folder, titled by the folder name with the full path as a tooltip; a session in its own worktree belongs to the folder it was opened from, not to its worktree folder, see "Worktree per session"; if two folders share a name the title is "parent/name"; groups ordered by most recent activity, sessions inside by recency; the folder line under each name is hidden, and a worktree session still shows its branch there). The choice is per browser (localStorage `claude-gui.sidebar-grouping`: `date` | `project`). Search works the same in both groupings. The switch is not shown while the archive is shown, which has no grouping.
- Frontend plus one accepted field on the existing PATCH route. The UI changes on the server broadcast (no optimistic update).
- Code: `public/js/session-groups.js` (grouping), `sidebar.js`, `session-actions.js` (`setPinned`), `chrome.js` (menu item), `app.js` (`onPin` for the topbar, `onRegroup`, and `actions` given to the sidebar), `icons.js` (`pin`), `css/layout.css`, `updateSession` in `lib/session-service.js`.

## Prompt templates (confirmed permanent, 2026-10-27)
The user saves prompts they reuse, with variables, picks them from the composer's "+" menu and manages them in a panel. No model call, no tokens.
- Storage: on the server in `data/templates.json` (next to `sessions.json`, honors `CLAUDE_GUI_DATA`), so templates survive a browser reset and every tab sees the same list. Not per browser, unlike the notification and grouping preferences. Written atomically (temp file + rename).
- Template: id, name (not empty, up to 80 characters), text (up to 20000 characters). At most 200 templates (the 201st is refused, HTTP 409). The list is newest first.
- Server: `GET /api/templates`, `PUT /api/templates/:id` (create or update; the BROWSER generates the id with `crypto.randomUUID`; the server accepts ids matching `/^[\w-]{1,64}$/`), `DELETE /api/templates/:id` (404 when missing). PUT and DELETE pass the existing Origin check.
- Variables: `{{name}}` placeholders; a name is letters of any script (Hebrew or English), digits, space, `_` and `-`, up to 40 characters. Variables are unique and ordered by first appearance; a repeated variable is asked once and filled everywhere.
- Using a template with variables opens a small form (one field per variable). Enter = next field / confirm, Shift+Enter = newline, Esc or cancel = nothing is inserted. A template without variables is inserted directly.
- The filled text is INSERTED into the composer and never sent automatically, so the user can still edit it. Rule everywhere (menu and panel): an empty composer is replaced, a composer with a draft gets the text appended.
- UI: "+" menu item "תבניות פרומפטים" opens a searchable list (Enter picks the first visible) with "ניהול תבניות…"; the settings panel "תבניות פרומפטים" (id `templates`, group session) creates, edits, duplicates, deletes and uses templates, and shows "שמירת ההודעה הנוכחית כתבנית" (prefilled from the composer) when the composer has text.
- Code: `lib/templates.js`, routes in `lib/api-routes-tools.js`, `public/js/templates.js` (variables, fill form, pick menu), `public/js/panels/panel-templates.js`, `public/js/panels/registry.js`, `chip-menus.js` ("+" menu), `api.js`, `actions.js` (`composerText`), `app.js`, `css/panels.css`.

## Per-turn changed-files summary (confirmed permanent, 2026-10-27)
After each turn the user sees which files Claude changed in THAT turn, and can open that turn's diffs only (not the whole git diff). Frontend only: recomputed from the session's items, nothing extra is stored and no server change.
- A card "Files changed in this turn" appears after the turn's `result` item, in history (re-rendered sessions) and for live turns. A turn is everything from the last user item to the result; a mid-turn correction item (`correction: true`) is not a user item for this purpose, so it does not start a new turn (see "Mid-turn correction"). Turns without file edits show nothing. The card stays visible in focus view (it is the turn's outcome).
- Counted: the edit tools Claude called — Edit, MultiEdit (its edits merged), Write, NotebookEdit — at top level and inside subagents. Calls whose tool result is an error (denied or failed) are skipped. Several edits to the same file are merged into one row.
- Header "שונה קובץ אחד" / "שונו N קבצים". One row per file: name (LTR, full path as tooltip) and +added / −removed line counts. Write counts all its lines as added and gets the badge "נכתב" (not "חדש": the GUI cannot tell a new file from an overwrite). NotebookEdit counts the lines of `new_source` as added and shows the raw cell text.
- Clicking a row expands that file's diffs from this turn only (reusing `diffLines` / `renderDiff` of `render-tools.js`). A "הכול" toggle expands all. A separate button "כל השינויים" opens the Changes pane (all uncommitted changes of the folder; see "Changes pane with line comments"). It was "git diff" and opened the settings-modal git panel until the Changes pane shipped (2026-10-27).
- Limit, said in a tooltip: only what Claude's edit tools wrote is shown. Files changed by Bash commands appear in the Changes pane, not in this card.
- A turn that continues after a mid-turn `result` (a correction still waiting when the result came, see "Mid-turn correction") has several result items; each is counted back to the last real user item (correction items do not count as one), so a later result's card can list files of the earlier part too. Not separately checked in a browser with a held turn.
- The card nodes carry no `data-item-index`, so search hits and item indexes are unaffected.
- Code: `public/js/turn-changes.js`; rendered by `thread.js` after result items (history in `show`, live in `append(item, index, items)`); `events.js` passes `session.items`; `app.js` passes `onOpenGit` (it opens the Changes pane); `css/messages.css`.

## Model server health indicator (confirmed permanent, 2026-10-27)
A small dot in the sidebar footer, next to the Claude Code version label, tells at once whether the model server behind `ANTHROPIC_BASE_URL` (for example a local qwen on Ollama or LiteLLM) is up, so a failed turn can be told apart from a server that is down. No model call, no tokens.
- States: green = up, red = down, grey = unknown. Unknown = the base URL is Anthropic's own (or empty): no request is made at all, the cloud is never pinged.
- The check is the same read-only `GET {ANTHROPIC_BASE_URL}/v1/models` that the model list uses (4 s timeout, same auth headers), and only for a custom base URL. There is no `/api/tags` fallback for health.
- Up = a 2xx answer. Down = no answer within 4 seconds ("אין תשובה תוך 4 שניות"), a connection error (its code, for example ECONNREFUSED), or ANY non-2xx answer ("השרת ענה HTTP 401"): a server that answers 401 or 404 cannot be used by Claude Code either.
- Server: `GET /api/model-health[?refresh=1]` -> `{ state, latencyMs, error, url, checkedAt }`. Cached 15 s, so many tabs do not multiply requests; `refresh=1` bypasses the cache. The displayed `url` has no user:password and no query. The token and key are sent only as request headers and are never returned.
- Tooltip on the dot: the URL, the latency and the error. Click = check now (refresh) plus a toast.
- When it checks: on page load, every 60 s while the tab is visible (paused while hidden, resumes when visible), right after a turn ends with an error (silent, no extra notification), and on a click. One request at a time.
- Code: `lib/model-health.js` (`checkModelServer(config, {refresh})`), `envOf` / `isAnthropic` exported from `lib/model-list.js`, route in `lib/api-routes-tools.js`, `modelHealth(refresh)` in `public/js/api.js`, `public/js/model-health.js`, the `#model-health` button in `public/index.html`, `css/layout.css`, `createModelHealth` and `eventView.onTurnFailed` in `app.js`, `view.onTurnFailed()` called from `events.js`.

## File viewer (confirmed permanent, 2026-10-27)
Clicking a file path in a tool row opens the file's CURRENT text in a read-only viewer with line numbers and the relevant lines highlighted. No model call, no tokens.
- Where: an open button on the tool row of Read, Edit, MultiEdit, Write and NotebookEdit (it does not toggle the row), and on each row of the per-turn changed-files card. Grep, Glob and Bash are NOT linked (their path is usually a folder or a command). Right-click on these buttons and on the Changes pane's file headers opens a file menu whose first item is "פתיחה בצופה" (see "Context menus for sessions and file paths").
- Dialog: path, "N שורות · M מסומנות", copy path, copy content, close (Esc or backdrop). Monospace, left-to-right, line numbers, marked lines scrolled into view. Plain text only: no syntax highlighting (no library), and the content is set with `textContent`, never HTML (a `<script>` in a file is shown as text).
- Marks: Read marks `offset` to `offset+limit-1` when given (else nothing); Edit marks where `new_string` now appears, MultiEdit each `new_string`, found by searching the current content; Write marks the whole file; NotebookEdit opens the raw JSON with no marks; the changed-files card marks each diff's added block. Text not found (the file changed since) shows the file with no marks and no error. The viewer shows the file as it is now, not as it was when the tool ran.
- Server: `GET /api/file-view?sessionId=&path=` -> `{ path, content, totalLines, truncated, size }`. Read-only, no body. Any `cwd` query parameter is ignored.
- Allowed only inside the session's folder, its extra folders (`addDirs`) and the uploads folder (the places Claude works in without asking). The roots come from the session on the server, never from the request. Real paths are compared with a separator boundary (`/proj` does not match `/proj-evil`), case-insensitive on win32 and darwin, after `realpath`, and the file is read from the resolved path, so `..` and symlinks cannot escape. Relative paths resolve against the session cwd; surrounding quotes are stripped.
- Errors: missing 404; directory 400; outside the folders 403 "הקובץ מחוץ לתיקיות של הסשן"; binary (NUL in the first 8 KB) 415. Reads up to 2 MB; larger returns the first 2 MB with `truncated: true` and the dialog says so. `totalLines` does not count the final newline. The dialog renders at most 20000 lines and says when it cut.
- Known nit: the 2 MB cut can split a multibyte character (one replacement character at the very end of a truncated file).
- Security: the first GET that returns file contents. Cross-site pages cannot read the response (no CORS; Host and Origin checks), and a local program with API access can already run commands through a session. See ARCHITECTURE.md -> Security.
- Code: `lib/file-view.js`, route in `lib/api-routes-tools.js`, `public/js/api.js` (`viewFile`), `public/js/file-viewer.js` (dialog and one delegated listener `enableFileLinks`, wired in `app.js`), buttons in `render-tools.js` and `turn-changes.js`, `css/panels.css` (viewer), `css/messages.css` (buttons).

## Per-turn stats (confirmed permanent, 2026-10-27)
Each finished turn shows its performance on the `result` meta line. With a local model the cost is irrelevant but the speed matters. Per turn only: no session totals (the usage panel keeps session cost and context). No model call.
- Line, in this order: total time · output tokens per second · "input → output טוקנים" (input includes cache read and cache write) · rounds (only when more than 1) · tool calls ("כלי אחד" / "N כלים", hidden at 0) · cost (only when above 0).
- Speed = output tokens divided by API seconds (time spent waiting for the model). When API time is unknown it uses total seconds; the tooltip then adds "(לפי הזמן הכולל)".
- Native `title` tooltip with the breakdown: total time, model time and tools/other time (only when API time is known), input, cache read, cache write, output, speed, rounds, tool calls, cost. The tooltip always lists rounds and tool calls even when the line hides them.
- Old saved items degrade gracefully: no API time means speed from total time; no cache fields count as 0; `usage` null shows time only. A failed turn keeps the unchanged "נכשל" line.
- Tool calls are counted on the frontend (nothing stored): `tool` items, top level and inside subagents, from the last user item back from the result, skipping mid-turn correction items (`isTurnStart` in `turn-stats.js`; same turn boundary as the changed-files card). With a held turn each result line counts back to the same user item.
- Server stores three more fields on the `result` item: `durationApiMs` (from `duration_api_ms`), `usage.cacheRead` and `usage.cacheWrite` (from `cache_read_input_tokens` and `cache_creation_input_tokens`).
- The result node keeps its `data-item-index`, so search is unaffected.
- Code: `public/js/turn-stats.js` (`turnStats`, `countToolCalls(items, resultIndex)`), `renderResult` and `appendItem(container, item, context)` in `public/js/render-items.js`, `resultContext` in `public/js/thread.js`, `translateResult` in `lib/event-translator.js`.

## Images in resumed conversations (confirmed permanent, 2026-10-27)
Importing a past CLI conversation ("שיחות קודמות", `lib/transcripts.js`) shows the images the user sent in it, instead of the "[תמונה]" marker. Server only; the existing thumbnails and full-size view are reused. No model call.
- On import, each base64 image block (PNG, JPEG, GIF, WebP) of a typed user line is stored through `saveImages` in `lib/images.js` (same rules: magic bytes must match the type, up to 5 MB) and attached to the user item as `images: [{ id, mediaType, name }]`, exactly like a message typed in the GUI. An image-only line has empty text plus `images`.
- Images are stored one by one (one `saveImages` call each), so the 10-per-call cap does not apply: one imported message can hold more than 10 images. Imported items are never re-sent, so this is harmless.
- An image that fails validation, or that is given by URL or file reference instead of base64, keeps a marker in the text ("[תמונה]" / "[N תמונות]", counting only the failed ones) and the reason is logged ("[transcripts] image not imported: ...").
- Lines whose text starts with "<" (command output and the like) are unchanged: no marker, nothing stored.
- Listing and titles keep the text marker and decode no images; images are stored only on import.
- Deleting the session removes its imported images (cleanup by references); unreferenced ones are swept at startup.
- Known limits: images inside tool results (for example Claude reading an image file) still show "[תמונה]" in the tool output; re-importing the same transcript stores the images again with new ids; images of items cut by the 3000-item import cap become unreferenced and are swept at startup.
- Code: `imageBlocks`, `userText(line, markedImages)`, `storeImages`, `userItem` in `lib/transcripts.js`.

## Split view (confirmed permanent, 2026-10-27)
The user can watch and drive two sessions side by side, for example one planning and one executing. Frontend only, no server changes: the server already streams every session's events to the browser. No extra model call.
- Toggle: a topbar button (icon `columns`, tooltip "פיצול תצוגה: סשן נוסף לצד זה (Ctrl+Shift+\)") and Ctrl+Shift+\ open or close a second pane beside the main thread; the pane's close button has the tooltip "סגירת הפיצול (Ctrl+Shift+\)". Ctrl+\ used to be the split toggle; since 2026-10-27 it closes the focused workspace pane (see "Workspace panes and session details rail"). Below 1000 px the toggle refuses with a toast, and an open split closes when the window gets that narrow.
- The pane has a header (session picker listing the other sessions that are not archived, "פתיחה בחלון הראשי" swap, close), its own live thread (streaming text, thinking, tool rows, working line, changed-files card, stats, file viewer links; thinking and tool rows as that session's transcript view mode shows them, see "Transcript view modes"), the session's own permission / question / plan cards, and a compact composer: text, send, stop. Enter sends, Shift+Enter is a newline; while that session works Enter (and the send button) sends a mid-turn correction and Alt+Enter queues the message on the server for the end of the turn, like in the main composer (see "Mid-turn correction"); stop returns the queued texts to the box. The "כל השינויים" button of the pane's changed-files card swaps the session into the main pane and opens the Changes pane.
- Pane composer limits, on purpose: no attachments, no slash menu or GUI commands, no `@` mentions, no model / mode chips, no `/btw`. A message that starts an outward slash command gets the same confirmation as in the main composer. To use those, swap the session into the main pane.
- The same session is never in both panes: choosing the main session in the picker swaps them; picking the pane's session in the sidebar changes only the main pane, and the pane then shows an empty state. A sidebar pick (a click) always changes the main pane only; the one explicit way to target the pane from the sidebar is the row menu item "פתיחה בחלון המפוצל" (it opens the split when closed, refuses below 1000 px with the same toast, is not offered for the main session or for archived sessions; see "Context menus for sessions and file paths"). Choosing a session into the pane clears its unread mark. A session that is archived while it is in the pane (or whose saved id is archived at reload) leaves the pane empty; restore it, or open it in the main pane.
- Events of the pane's session (item, delta, status, runtime, permission, permission-resolved) update the pane as well as the main thread. Notifications treat a pane session as on screen (see Notifications); a third session still notifies.
- The `/btw` card, the search-hits bar and the view-mode controls (Ctrl+O, the "עוד" menu; see "Transcript view modes") belong to the main pane only. So do the workspace panes and the session details rail (see "Workspace panes and session details rail"): the split pane has none.
- Per browser (localStorage): `claude-gui.split-open` and `claude-gui.split-session`; reload restores both.
- Code: `public/js/split-view.js` (`createSplitView`), `public/css/split.css`, `<aside id="split-pane">` in `public/index.html`, the split button in `chrome.js` (icon `columns` in `icons.js`), routing in `events.js` (`view.paneThread`), `notify.js` (`onScreen`), wiring in `app.js`, Ctrl+Shift+\ in the shortcut table (`shortcuts/shortcut-list.js`, handled by `shortcuts/bind-shortcuts.js`).

## Workspace panes and session details rail (confirmed permanent, 2026-10-27)
The main session has a pane area beside the chat, like the Code tab of Claude Code Desktop, and the session details rail is the first pane in it. Later panes (Terminal, Files, Plan, Background tasks) plug into the same area; the Changes pane is the second one (see "Changes pane with line comments"). The rail makes no model call and costs no tokens.
- Layout: under the topbar a row holds the chat (thread and composer) and the pane area. In RTL the area is on the physical left of the chat. Open panes are stacked in one column, each with a header (title, close). Dragging the edge that faces the chat resizes the column (mirrored in RTL).
- Open and close: a topbar button (icon `panel-right`, shown pressed while open, title "הצגת / הסתרת פרטי הסשן") and the same item in the topbar "עוד" menu. The rail is open by default.
- Per browser (localStorage): `claude-gui.panes-open` (list of open pane ids, default `["details"]`) and `claude-gui.panes-width` (default 340 px, minimum 280 px; the maximum keeps the chat at 560 px or more).

## Changes pane with line comments (confirmed permanent, 2026-10-27)
The main session has a "שינויים" pane, like the diff view of Claude Code Desktop: the folder's uncommitted changes file by file, with comments on single lines that the user sends to Claude together. Viewing makes no model call; sending is an ordinary message (an ordinary turn).
- Opening: the rail's Changes card (click), the topbar diff icon (now the pane's toggle, shown pressed while open, title "שינויים (Ctrl+Shift+D)"; it no longer opens the git panel), Ctrl+Shift+D (matched by the physical D key, so it works on a Hebrew layout; bound in `public/js/shortcuts/bind-shortcuts.js` through the table in `shortcuts/shortcut-list.js`), the "כל השינויים" button of the per-turn changed-files card, and the same button on the split pane's card (swaps that session into the main pane first). The buttons only open the pane, never close it; the toggles close it. The settings-modal git panel stays (`/diff`, settings) and still shows staged and unstaged changes as separate diffs. Width, stacking, persistence and the room rule are those of the panes (see "Workspace panes and session details rail"); the topbar redraws after any open or close, including the pane's own X.
- What it shows: everything not yet committed in the session folder's repository against HEAD, staged and unstaged merged into one diff per file, plus new files that git does not track yet, shown as added files (so they show here although the rail counts them only as files). It covers the WHOLE repository from its top level: a session in a subfolder sees every changed file, with repo-relative paths. It includes changes not made in this session (by the user or by Bash). A repository without commits is compared with git's empty tree. Not a repository: "התיקייה של הסשן אינה מאגר git." (a folder that no longer exists says so, as in the rail); nothing changed: "אין שינויים שלא נשמרו ב-commit."; a failed request shows its error.
- Per file: a collapsible header (chevron, status "חדש" / "נמחק" / "שם חדש" / "שונה", path left-to-right with the old path in the tooltip for a rename, +N −M, "N הערות" when it has comments), then the hunks with the old and the new line number of each line. A binary file says "קובץ בינארי."; a file without content changes (mode, rename, empty file) says "אין שינויי תוכן (הרשאות, שם, או קובץ ריק)." The toolbar shows "N קבצים", the total +added −removed of the shown diff, a hint "+ ליד מספר שורה מוסיף הערה" while there are no comments, and a refresh button. Collapsed files are remembered in memory per session. The rail's counts (git numstat, untracked files as files only) and the toolbar's (the shown diff, new files' lines included) can differ. Right-click (or Shift+F10) on a file header opens the file menu (see "Context menus for sessions and file paths").
- New (untracked) files: listed by `git ls-files --others --exclude-standard` (so `.gitignore` applies), at most 100 files, each up to 512 KB, 2 MB read in total per request. Symlinks are not followed. A binary file (NUL in its first 8 KB) is shown as "Binary files"; an empty file has no lines. Files not shown for these reasons are counted: "N קבצים חדשים לא מוצגים (גדולים, רבים מדי או קיצורי דרך)."
- Large diffs: the whole diff is cut at 300000 characters; the pane says "השינויים גדולים מדי – מוצג רק חלקם." and files after the cut are missing.
- Names and format: non-ASCII names (Hebrew) are shown as they are (git runs with `core.quotepath=false`, which also applies to the git panel and the rail); names with quotes, backslashes or tabs come C-quoted from git and are decoded. Paths with spaces, CRLF files, renames, new, deleted and mode-only files are handled, and content lines that begin with `--` or `++` are content. The diff is requested with fixed `a/` `b/` prefixes whatever the user's git config says.
- Refresh: drawn when a session is first shown, when another session is shown, when the session's status changes (a turn starts or ends) and on the refresh button. No timers; one request at a time per session. The pane is redrawn only when the diff text changed, so a half-typed comment keeps its text and focus across a turn end.
- Line comments: hover a line and click the "+" beside its number (each line shows its old and its new number) to open a box; Enter adds the comment, Shift+Enter is a new line, Esc cancels and does NOT stop Claude's running turn; Enter during IME composition does nothing. One box is open at a time: opening another drops the first one's unsaved draft. An added comment shows under its line with a delete button; a comment cannot be edited, only deleted and written again.
- Where a comment lives: it is anchored by file path, side (the new line, or the old number for a deleted line), line number and the line's text. After a refresh a comment stays on its line only while that line still reads the same; otherwise it moves to "הערות על שורות שהשתנו מאז:" under its file, and a comment whose file left the diff is listed at the top under "הערות על קבצים שכבר אינם בשינויים:". Such comments stay deletable and are still sent; they are never dropped silently.
- Not persisted: comments live in the browser's memory per session, so a reload loses them (like `/btw`). Switching sessions keeps each session's own comments.
- Sending: the footer shows "N הערות", "ניקוי" (clears them all) and "שליחה ל-Claude" (tooltip Ctrl+Enter). Ctrl+Enter (or Cmd+Enter) works while the focus is inside the pane, the comment box included, and only there: the composer's own Ctrl+Enter is untouched. A draft still open in the box is added first. All comments go as ONE message through the normal send path with no `delivery`, so it is queued while Claude works and sent at the turn's end, NOT as a mid-turn correction (the comments cite diff lines the running turn may still change; decided in Stage 1 without asking the user, see "Mid-turn correction"): the first line "הערות על השינויים (N) — תקן לפי ההערות:", then per comment "- file:line", the line's text quoted with ">" (up to 200 characters, then "…") and the comment; a deleted line is cited as "file, שורה N בגרסה הקודמת (שורה שנמחקה)". The message never starts with "/". One send at a time per session (the send button is disabled meanwhile). The comments are cleared only after a successful send; after a failure they stay. Claude then edits the files and the turn end refreshes the pane with the new diff.
- Server: `GET /api/sessions/:id/diff` -> `{ isRepo, diff, truncated, newFilesSkipped, root }` (`root` = the repository's top level, added in D7 so a file header's full path is `root` + the repo-relative path even for a session started in a subfolder; `{ isRepo: false }` outside a repository). Read-only, no body. The folder is the session's own, from the server; there is no `cwd` parameter; an unknown session is 404; a folder that no longer exists answers `{ isRepo: false, folderMissing: true, archived }`. git runs with the safety flags of the git panel. Unlike `/api/file-view` it is not limited to the session folder: it covers the whole repository, and reads the text of new files (up to the limits above). See ARCHITECTURE.md -> Security.
- Known limits: no replies, suggestions or comment editing; comments are lost on reload; a very large diff shows only the first 300000 characters; new files beyond the limits are not shown.
- Not checked: light theme; the real CLI and real model with a comment message; the last fix (the in-flight send flag is kept per session, so another session's button stays enabled) was not re-run in the browser.
- Code: `public/js/panes/pane-changes.js` (`createChangesPane`), `diff-parse.js` (`parseDiff`, pure), `diff-view.js` (one file's table, "+" button, comment box and bubbles), `diff-comments.js` (per-session comments and `composeMessage`), `changes-chrome.js` (toolbar, notes, footer), `session-fetch.js` (`createSessionFetch`, also used by the rail), `panes/pane-host.js` (`open(id)`, `onChange`) and `panes.js`; `public/css/changes-pane.css`; server `lib/git/session-diff.js` (`sessionDiff`), `core.quotepath=false` in `lib/git/run.js`, the route in `lib/api-routes-tools.js`, `sessionDiff` in `api.js`; the topbar toggle in `chrome.js`, Ctrl+Shift+D in `shortcuts/bind-shortcuts.js` (table: `shortcuts/shortcut-list.js`) and the wiring in `app.js`, the button in `turn-changes.js`, `openChanges` in `split-view.js`, the rail card in `pane-details.js`.

## Transcript view modes (confirmed permanent, 2026-10-27)
The user chooses how much of Claude's work the thread shows, like "Transcript view" in the Claude Code Desktop Code tab. Frontend only: no server change, no model call, nothing sent to the CLI.
- Three modes, Hebrew labels: "רגילה" (Normal, the default), "חשיבה" (Thinking), "מפורטת" (Verbose). User messages, Claude's text answers, notices, errors, command output, the todo card, the per-turn changed-files card and the stats line show in every mode. The permission, question and plan cards are not part of the thread and are not affected.
- Normal: a run of two or more consecutive top-level tool rows collapses into ONE closed group row; all thinking is hidden (also a subagent's inside its open row). A hidden thinking does not split a run.
- Thinking: the same grouping, and thinking blocks are visible; a visible thinking block splits a run. The mode is offered only once the session has produced thinking at the top level (a subagent's own thinking does not count). Until then Ctrl+O skips it, its menu entry is disabled, and a saved "Thinking" shows as Normal.
- Verbose: no groups. Every top-level tool row is open, also rows that arrive live; thinking is visible. Leaving Verbose closes those rows again (rows the user opened by hand in another mode stay open).
- Group row: "N כלים" (N = the run's top-level tool calls), then the tools' Hebrew verbs with ×N for repeats (for example "קריאה ×2, עריכה"), and a state icon: spinner while any call runs, red x when any failed, check otherwise. Opening the group shows the original rows, which work as before (open, file-viewer button). A lone tool row is not grouped. A subagent's rows stay inside their parent row and are never grouped. Any other item (text, user message, notice, todo card, result) ends a run.
- Per session, per browser: localStorage `claude-gui.transcript-view` as `{ sessionId: mode }`, newest last, at most 300 entries. A session without an entry is Normal. Switching sessions applies each one's own mode.
- Changing the mode: Ctrl+O cycles Normal, Thinking (when offered), Verbose and shows the toast "תצוגת תמליל: <label>". It uses the physical O key (works on a Hebrew layout), works while typing in the composer, and always stops the browser's "open file" dialog. It is ignored with Shift or Alt (Ctrl+Shift+O stays "new session"), a held key cycles once, and with no open session it does nothing. It cycles from the mode on screen, so it works when browser storage is blocked. The topbar "עוד" menu starts with the section "תצוגת תמליל (Ctrl+O)": the three modes, each with a short description and a check on the current one; a "סשן" header precedes the older items.
- Split view: each thread applies its OWN session's saved mode. The pane has no control for it; Ctrl+O and the menu change the main session only. To change the pane session's mode, swap it into the main pane.
- `/focus` is unchanged and independent: it also hides the groups, tool rows, thinking and notices, in whatever mode is set. Kept separate on purpose (see DECISIONS.md).
- Search: a hit inside a closed group or tool row opens it (and any closed rows around it) before scrolling to it; the mode does not change. A hit on a node the mode hides is skipped (defensive: thinking is not searched).
- Known consequences: in Normal and Thinking a tool row sits inside a closed group, so its file-viewer open button needs the group opened first (the rows of the changed-files card keep theirs). The group's count covers that run's top-level calls; the result line's "N כלים" (Per-turn stats) counts the whole turn including subagents' calls, so they can differ. The default look changed from "everything shown, rows closed" to Normal.
- Not checked: the real CLI, the light theme, a real session with very many tool rows (the whole thread is regrouped when a mode is applied; its cost on very long sessions is unmeasured).
- Code: `public/js/transcript/` (`view-mode.js` modes, labels, saved mode, menu entries, next mode; `tool-groups.js` grouping and summaries; `transcript-view.js` `createTranscriptView(messages)`, one per thread, sets `messages.dataset.view`; `reveal.js` `revealNode` / `canReveal`), `public/css/transcript.css`; `thread.js` (creates the view, `show` / `append` / `setRunning(false)` call into it, returns `view`), `chrome.js` (menu section, `viewMode` / `onViewMode` handlers), `search-hits.js`, `public/js/shortcuts/bind-shortcuts.js` (Ctrl+O, through the table in `shortcut-list.js`), `app.js` (wiring and the toast).

## Worktree per session (confirmed permanent, 2026-10-27)
A new session can run in its own git worktree, like Claude Code Desktop, so sessions working in parallel never touch each other's files. Plain git only: no pull requests, no push, no fetch, nothing leaves the machine. No model call.
- Welcome page: a switch "worktree נפרד" (branch icon) under the folder picker. It is enabled only when the folder is inside a git repository that has at least one commit and is not bare; otherwise it is disabled with the note "התיקייה אינה מאגר git" or "אין עדיין commit במאגר". When enabled the note says "ענף חדש מ-<branch>", and the tooltip explains the feature (separate copy on a new branch, starts from the current commit, uncommitted changes and git-ignored files are not copied). Default off; the choice is per browser (localStorage `claude-gui.worktree`). The folder is checked by `POST /api/worktree/probe` `{ cwd }` -> `{ isRepo, hasCommits, branch }` (Origin-checked; a non-string `cwd` is 400); the browser caches an answer for 30 s. Warm-up (typing starts a spare CLI) is skipped for a folder where a worktree will be made, because the session runs in a folder that does not exist yet.
- Creating: with the switch on and the folder able, sending the first message creates the worktree first (toast "יוצר worktree…"): `POST /api/sessions` with `worktree: true`. If anything fails, no session is created and the Hebrew error is shown. Only the boolean `true` counts; the request cannot carry a `worktree` object, `claudeSessionId`, `items` or `forkPending` (ignored). Importing from "שיחות קודמות" never creates a worktree.
- Place and name: `<main checkout>/.claude/worktrees/<YYMMDD-xxxx>` (date and 4 random hex digits, ASCII and short because of Windows path limits) on a NEW branch `worktree-<YYMMDD-xxxx>`: the layout and naming of `claude --worktree`. The main checkout is the first entry of `git worktree list`, so a folder inside another worktree never nests one in it; a bare repository is refused. The name is free as a folder and as a branch (8 tries) and the command is `git worktree add -b` (never `-B`), so an existing branch, such as one kept after a removal, is never reset.
- Base: the chosen folder's current commit (HEAD), local. Nothing is fetched; the CLI's own default (origin after a fetch) is not used. Uncommitted changes and files git ignores (`.env`, `node_modules`, `settings.local.json`) are NOT copied; submodules are not initialized (git's behaviour).
- Subfolder: a session opened from a subfolder of the repository runs in the same subfolder of the worktree (compared by real path; a symlinked path, or one not inside the checkout, gives the worktree's root without a notice). A subfolder that is not in HEAD gives the worktree's root and the session comes back with a notice, shown as a toast: "תת-התיקייה שנבחרה אינה ב-commit, ולכן הסשן נפתח בתיקייה הראשית של ה-worktree."
- Safety when creating: a symlink at `.claude`, `.claude/worktrees` or the target is refused (as the CLI does). The line `/.claude/worktrees/` is appended once to `<git-common-dir>/info/exclude` (local to this clone, never a tracked `.gitignore`; best effort, a failure only logs), so the main checkout's rail, Changes pane and `git status` do not list the worktrees. The repository's own hooks and filters DO run during the checkout (post-checkout, LFS), as with the CLI and `git checkout`; fsmonitor stays off. Time limit 3 minutes. A failed add that left a complete worktree (for example a failing post-checkout hook) is cleaned up: the worktree is removed, pruned, and the branch THIS add created is deleted; the message says which case it was.
- The session: `session.worktree = { path, branch, root, source }` (`source` = the folder the user chose) or `null`, saved in `data/sessions.json` and in the session meta; `cwd` is the worktree folder (or its subfolder). A fork inherits `worktree` and works in the same worktree. The details rail, the Changes pane and the file viewer work on the worktree, because it is the session's folder.
- Shown: the topbar has the project folder chip (the folder the user opened, not the worktree) and a branch chip with a branch icon beside it (click copies the worktree path; tooltip: branch and path). The sidebar row's second line is "folder · branch" (under "לפי פרויקט" only the branch). Grouping by project, the folder line and search use the project folder, and search also matches the branch. The rail's Environment card shows the project folder, a "worktree" row (click copies the path) and the branch ("ענף").
- Deleting a session in a worktree: after "למחוק את ...?" a second question "להסיר גם את ה-worktree?" is asked, but only when no other session (a fork) works in the same worktree. It names the folder and the branch, says that files git ignores (such as `node_modules`) go with the folder, that uncommitted changes keep the folder, and that the chat cannot be resumed from "שיחות קודמות" afterwards. Buttons "הסרת ה-worktree" (danger) and "להשאיר"; Esc keeps it. The session is deleted in every case. (Archiving a session also removes its clean worktree, without a question; see "Archived sessions".)
- Removing: `DELETE /api/sessions/:id?worktree=remove` (exactly that value; anything else keeps the folder) -> `{ ok, worktreeRemoved, worktreeError? }`. The server removes only the path stored on the session, never one from the request, after checking by real path that it is under `<root>/.claude/worktrees` and that git lists it. It runs `git worktree remove` WITHOUT `--force`, retried up to 5 times, 500 ms apart, for a Windows lock. Uncommitted or untracked changes keep the folder (error "יש בו שינויים או קבצים חדשים שלא נשמרו ב-commit."). A folder deleted by hand is pruned and counts as removed. The BRANCH IS NEVER DELETED by the user's actions. Toasts: "ה-worktree הוסר. הענף <branch> נשמר." or, in the error style, "ה-worktree נשאר ב-<path>: <reason>".
- Known limits: git-ignored files are not copied (no `.worktreeinclude`); the lock retry on Windows, a partly deleted folder and LFS are untested; the real CLI was not reported as run inside a worktree (Stage 3 used the fake CLI, as for the whole batch); if the CLI process still holds the folder the removal may be refused (the folder stays, the toast says so); a worktree whose session was deleted without removing it is no longer shown anywhere in the GUI (the toast gave its path).
- Security: the first git WRITES of the GUI (`worktree add`, a file append to `info/exclude`, `worktree remove`); see ARCHITECTURE.md -> Security.
- Code: `lib/git/worktree.js` (`probeWorktree`, `createWorktree`, and `restoreWorktree` for "Archived sessions"), `lib/git/worktree-paths.js`, `lib/git/worktree-remove.js` (`removeWorktree`, also used by archiving), `git(cwd, args, { timeoutMs })` in `lib/git/run.js`; `startSession` and `deleteSession(id, { removeWorktree })` in `lib/session-service.js`, the `worktree` field in `lib/session-store.js`, routes in `lib/api-routes.js` and `lib/api-routes-tools.js`; `public/js/worktree/` (`worktree-toggle.js` the switch, `worktree-delete.js` the second question, `project-folder.js`), `session-actions.js` (`createFromDraft`, `remove`), `chrome.js` (welcome switch, chips), `sidebar.js`, `session-groups.js`, `session-search.js`, `panes/pane-details.js`, `warm-up.js`, `api.js`, `ui.js` (`ask({ cancelLabel })`), `public/css/worktree.css`.

## Archived sessions (confirmed permanent, 2026-10-27)
The user puts a finished session away without deleting it, and can bring it back, like Archive / Archived in the Claude Code Desktop Code tab. No model call.
- Archiving: from the topbar "עוד" menu ("העברה לארכיון") and from the item "העברה לארכיון" of the sidebar row's "⋯" / right-click menu (D7 replaced D6's separate archive button; like Desktop: hover, open the row's menu, Archive). `POST /api/sessions/:id/archive` -> `{ worktreeRemoved, worktreeError? }`. The server sets `archived: true`, `archivedAt` and `pinned: false` FIRST, then stops a running turn (the turn ends as "stopped", nothing notifies), closes the session's CLI process (frees memory) and removes the session's worktree (see below). Both fields are saved in `data/sessions.json`. There is no confirmation, except when the session has running background tasks, which die with the CLI process: "להעביר את ... לארכיון?" with "N משימות רקע רצות בסשן, והן ייעצרו." If the open session is archived the view goes to the welcome page, but only after the server succeeded. Toast "הסשן הועבר לארכיון", or the same followed by "ה-worktree נשאר: <reason>" when the folder stayed.
- Queue: queued messages are kept, paused (not returned to a composer, not cleared). The end of a turn never sends them for an archived session (`dispatchNext` skips it); after a restore the composer shows "שליחת הבאה" as it does after a crash.
- The list: an archived session is not in the session list or in any of its groups. A button "ארכיון (N)" at the foot of the list (fixed at the bottom, only while N > 0) switches the list to the archive: one group "בארכיון", sorted by `archivedAt` (newest archived first), no grouping switch, no pin button, a restore button on each row (shown on hover) beside the row's "⋯" menu (its first item is the restore) and a back button "חזרה לסשנים". Search covers the list shown: the sessions, or the archive. The archive view lives in the page only (a reload starts on the sessions), and an emptied archive returns to the sessions by itself.
- Opening: an archived session opens normally (thread, details rail, Changes pane, search bar) with a topbar chip "בארכיון · שחזור"; the "עוד" menu shows "שחזור מהארכיון" instead of the archive item and its pin item is disabled. Sending a message, or "שליחת הבאה", restores it first and then sends: the one server rule (`restoreForMessage`) sits in the messages route and the queue-resume route, so the main composer and the Changes pane's comment send both go through it. `/btw`, control requests and warm-up do not restore.
- Restoring: the chip, the topbar menu item, the row button or the row menu's "שחזור מהארכיון"; `POST /api/sessions/:id/unarchive` clears `archived` and `archivedAt`. The session returns unpinned, to its place by last activity (restoring does not change its recency). A fork inherits neither `pinned` nor `archived`.
- Worktree (user decision 2026-10-27, "כמו בדסקטופ"; Desktop removes the worktree on archive): archiving removes the session's worktree folder with `removeWorktree` (never `--force`; the branch always stays), unless another session that is NOT archived (a fork) works in the same worktree. Uncommitted or untracked changes keep the folder and the toast gives the reason; Desktop's "Archive anyway" (discard the changes) and its removal of a kept worktree and its changes about 30 days after the session is archived or last opened (both as the main agent read them on the Desktop docs page) are not copied: a kept folder stays until the user removes it. Restoring checks the folder out again at the SAME path from the session's branch (`restoreWorktree`: `git worktree prune`, then `git worktree add <path> <branch>`; symlinks at `.claude`, `.claude/worktrees` or the target are refused; nothing to do while the folder exists), so the CLI conversation, which the CLI keeps per folder, carries on. If the branch no longer exists, or git fails (for example the branch is checked out elsewhere), the restore answers HTTP 400 with the Hebrew reason and the session stays archived.
- A session whose folder is gone (an archived session whose worktree archiving removed): the details rail and the Changes pane say "תיקיית הסשן לא קיימת כרגע: ה-worktree הוסר בהעברה לארכיון ויחזור בשחזור." (a non-archived session: "תיקיית הסשן לא קיימת."). `/btw`, control requests and warm-up answer HTTP 409 "הסשן בארכיון ותיקיית ה-worktree שלו הוסרה. שחזר אותו מהארכיון כדי להמשיך." and never start a CLI, so no failed start lands in the transcript; the command catalog of such a session comes from the folder it was opened from (`worktree.source`).
- Delete: unchanged (the "עוד" menu of an opened archived session, or since D7 the row menu's "מחיקה" for any row, with the worktree question of "Worktree per session"). Known: for an archived session whose worktree archiving already removed, the second question is still asked; answering "הסרת" is harmless (the server prunes and reports it removed).
- Other places: an archived session never notifies, is never marked unread and is left out of the tab-title count and the brand state (see "Notifications"); the split-view picker does not offer it (see "Split view"); running background tasks end as "killed" (see "Background tasks"); `PATCH` with `pinned` is ignored for an archived session.
- Known limits: the lock retry of `removeWorktree` after a graceful CLI close is untested on Windows (it degrades to the folder being kept, with the toast); the real CLI was not reported as run (the fake CLI, as for the whole batch); the light theme was not reported as checked; ignored files (`node_modules`, `.env`) go with a removed worktree and are not brought back by a restore; a restore fails when the branch was deleted by hand.
- Code: `lib/session-archive.js` (`archiveSession`, `unarchiveSession`, `restoreForMessage`), `restoreWorktree` in `lib/git/worktree.js`, `requireRunnable` in `lib/session-common.js` (used by `catalog-service.js`, `side-questions.js` and `warm` in `session-service.js`), `dispatchNext` in `lib/session-messages.js`, `updateSession` (ignores `pinned` when archived), routes in `lib/api-routes.js` and the git views in `lib/api-routes-tools.js` (`folderMissing`); `public/js/archive/archive-list.js` (the archive view, its switch and, since D7, `restoreButton` for archived rows; the archive action moved to the row menu), `sidebar.js`, `session-actions.js` (`archive`, `unarchive`), `chrome.js` (chip and menu items), `notify.js`, `events.js`, `page-status.js`, `split-view.js`, `warm-up.js`, `panes/pane-details.js` (`notRepoText`, also used by `panes/pane-changes.js`), `api.js`, `icons.js` (`archive`), `state.js` (`modelLabel` moved there from `app.js`), `app.js`, `public/css/archive.css`.

## Context menus for sessions and file paths (confirmed permanent, 2026-10-27)
Sessions and file paths have a context menu, like the per-row menu of the Claude Code Desktop Code tab ("hover over it in the sidebar, open its menu, and select Archive", as the main agent read on the Desktop docs page). Frontend only, apart from one field on the Changes pane's route. No model call.

## Mid-turn correction (confirmed permanent, 2026-10-27)
While Claude works, a message the user sends goes straight into the running turn, like Claude Code Desktop and the terminal (user decision by AskUserQuestion, "כשקלוד עובד ואתה שולח הודעה – מה יקרה?": "Enter = תיקון מיידי"; the Desktop/terminal parity is the user's statement, not checked in the docs). The old queue stays behind Alt+Enter. No extra model call beyond the turn itself.
- Keys: while a session's turn runs, Enter (and the send button) in the main composer and in the split pane's composer sends a CORRECTION; Alt+Enter sends the message to the GUI queue, which waits for the end of the turn (the former behaviour of Enter). When the session is idle both keys are a normal send. Enter during IME composition does nothing, as before. Shift+Enter stays a newline.
- Hints: the hint line ends "Enter בזמן עבודה – תיקון מיידי · Alt+Enter – לתור"; the send button's tooltip while running is "תיקון באמצע התור (Enter) – Claude יראה אותו בצעד הבא · Alt+Enter: לתור, אחרי שיסיים". The queue's own header text is unchanged.
- What a correction is: `POST /api/sessions/:id/messages` with `delivery: 'correct'` writes `{type:'user', message, uuid}` to the live CLI (only `uuid`; `priority` is omitted on purpose, the CLI's default for inbound messages is already "next"). The CLI queues it and drains it into the running turn at its next step. The server pushes a user item at once with `correction: true` and `correctionId` (the uuid); the thread shows it with the label "תיקון באמצע התור" (pencil icon) in a dashed bubble. Attachments work as for any message. The answer is `{ corrected: true }`.
- Fallback to the normal path: a correction is accepted only when the runtime can take it (`canCorrect`: the turn is active, the CLI was started with `--replay-user-messages`, the process is live and not closing). Otherwise the message is queued (session running) or starts a turn (idle), exactly as before. In particular a CLI whose `--help` does not list `--replay-user-messages` never gets corrections: Enter queues. The same holds in the CLI's start-up window before the turn is active. An absent `delivery` (every other sender: the Changes pane's comment send, the command runner) means queue.
- While a permission, question or plan card is pending a correction is allowed: the CLI keeps it and takes it in after the decision.
- Consumption: the runtime keeps the uuids of corrections not yet taken in. A replay user event (`isReplay`, same uuid) marks one as taken in. `lib/event-translator.js` still ignores replay events for the thread.
- Turn end: when a successful `result` arrives while corrections still wait, the CLI will run another turn for them, so the turn is HELD: the session stays "running" (`turnActive` stays true, so Stop and the idle timer behave), and no turn-end hook runs: no notification, no `dispatchNext` of the GUI queue, no model-health recheck. The result item itself is still stored and shown. An error or stopped result is never held. The fallback is 20 seconds (`HOLD_MS`): if no assistant or stream event (or replay) shows up, the tracking is cleared and the turn ends. If the CLI then starts a turn after all (a next turn that comes later than the fallback), the session is set to running again (`onTurnResume`) and ends normally.
- Stop (Esc or the stop button): the usual interrupt, and the waiting corrections are cancelled with `cancel_async_message {message_uuid}` (best effort, 3 s). For each correction Claude never saw the thread gets a notice "התיקון לא הגיע ל-Claude לפני העצירה: "…"". The GUI queue still returns its texts to the composer.
- Per-turn card and stats: a correction item is not a turn start (`isTurnStart` in `turn-stats.js`, also used by `events.js` and `turn-changes.js`), so the changed-files card, tool-call counts and notification outcome of a turn that received a correction still count the whole turn.
- Search, history (↑) and counts treat a correction item as an ordinary user message.
- Known limits: stop exactly during a hold when the CLI has no next turn clears the fallback, and the turn then ends only through `interrupt`'s 6 s kill timer (the process is killed and restarted by the next message); a correction item reloaded from a CLI transcript ("שיחות קודמות") shows as an ordinary user message; corrections are not persisted as waiting (a server restart or CLI exit clears the tracking); the order in the thread is the send order, the CLI's replay can come in the next turn.
- Not verified: the real CLI 2.1.246 (whether stdin honours `uuid`, whether the replay carries the same uuid, whether `cancel_async_message` and the interrupt sweep behave as assumed, how long a late next turn takes). If the uuid does not come back, the effect is a 20 s wait at the end of a turn that got a correction, not a break. The light theme and Windows were not checked. Everything was tested against `dev/fake-claude.js` (with `dev/fake-corrections.js`) only.
- Code: server `lib/runtime-corrections.js` (`setUp`, `canCorrect`, `send`, `noteEvent`, `holdTurn`, `dropWaiting`, `clear`), `lib/runtime-events.js` (`handleMessage`, `handleExit`, `endTurn`), `lib/runtime-permissions.js`, `lib/runtime-spare.js`, `lib/session-runtime.js` (`correct`, `dropCorrections`, the `onTurnResume` hook), `lib/session-events.js` (`onTurnResume`), `lib/session-messages.js` (`sendMessage(..., { delivery })`, `stopSession`), `lib/cli-process.js` (`send(content, { uuid })`), `lib/cli-args.js` (`--replay-user-messages` when listed), `lib/api-routes.js` (passes `delivery`); frontend `public/js/composer.js` (Enter / Alt+Enter, hint), `composer-queue.js` (`queueList`, `sendTitle`), `composer-history.js`, `composer-attachments.js`, `context-ring.js`, `main-composer.js`, `actions.js` (`send(text, attachments, delivery)`), `api.js` (`sendMessage(..., delivery)`), `split-view.js`, `render-items.js` and `css/messages.css` (label and bubble), `turn-stats.js` (`isTurnStart`), `events.js`, `turn-changes.js`, `shortcuts/shortcut-list.js`; tests `dev/fake-claude.js`, `dev/fake-corrections.js`, `dev/fake-catalog.js`.
