# Decisions

## [2026-10-27] Archiving removes the session's clean worktree and restoring checks it out again (user decision, like Desktop)
**Decision:** `archiveSession` (`lib/session-archive.js`) removes the stored worktree folder with `removeWorktree` (never `--force`, the branch stays) unless another session that is not archived (a fork) works in the same path. Uncommitted or untracked changes keep the folder and the toast gives the reason. `unarchiveSession` first calls `restoreWorktree` (`lib/git/worktree.js`): after a `worktree prune`, `git worktree add <path> <branch>` at the SAME path from the session's own branch; a branch that is gone, or any git failure, answers HTTP 400 and the session stays archived. There is no question on archive.
**Alternatives considered:** (1) Keep the worktree on archive and remove it only on delete (my Stage 1 proposal, and the user's first design: "restoring needs the folder"). (2) Desktop's "Archive anyway", which discards uncommitted changes. (3) Ask the D5 second question ("להסיר גם את ה-worktree?") on every archive. (4) Delete the branch as well.
**Why:** The user was asked (AskUserQuestion, "What happens to a session's worktree when it is archived?") and chose "כמו בדסקטופ"; the standing rule for the batch is to follow the Desktop Code tab, and the Desktop docs page (read by the main agent on 2026-10-27) says archiving may remove the worktree, with "Archive anyway" for uncommitted changes. That confirms the D5 note that was written from memory. The GUI keeps its D5 safety rules instead of copying the discard: no `--force`, so dirty or untracked changes simply keep the folder; the branch is never deleted, so the work is never lost; nothing is time-based. The docs page (as the main agent fetched it) says: "If Desktop asks about the changes: select Archive anyway to discard them, or cancel and commit them", and, in any other case, "the worktree stays on disk with its changes. For a local session, Desktop removes both about 30 days after the session is archived or you last open it, whichever is later." Neither the discard nor the 30-day removal is copied, so a kept folder stays until the user removes it. Restoring at the same path matters because the session's `cwd` is unchanged and the CLI keeps its conversation per folder, so `--resume` carries on. The cost: ignored files (`node_modules`, `.env`) go with the folder and a restore does not bring them back; a restore can fail (branch deleted by hand, branch checked out elsewhere) and then the session waits archived; the Windows lock after a graceful CLI close is covered only by the 5 x 500 ms retry of `removeWorktree` (untested there; it degrades to the folder kept plus a toast).

## [2026-10-27] An archived session opens normally, and sending a message restores it
**Decision:** An archived session opens like any other (thread, rail, Changes pane, search bar) with a topbar chip "בארכיון · שחזור". Sending a message, or "שליחת הבאה", restores it first (`restoreForMessage` in the messages route and the queue-resume route). `/btw`, control requests and warm-up do not restore.
**Alternatives considered:** (1) Read-only until the user presses "שחזור". (2) Open it only after restoring.
**Why:** The GUI has no read-only session concept, and read-only would have to be enforced at about eight entry points (main composer, split composer, Changes pane send, `/btw`, warm-up, control requests, queue resume, templates), where one missed path is a bug; "send restores" is one server rule at the point every send already passes. Reading an old chat and then continuing it is the common case. If Desktop were read-only, "normal" deviates harmlessly; the opposite mistake would block the user. Judged in Stage 1 without asking the user. The cost: an accidental message restores the session (the chip says so), and a restore re-creates the worktree, which can take a while.

## [2026-10-27] The queue of an archived session is kept, paused
**Decision:** Archiving stops a running turn but leaves `session.queue` alone. `dispatchNext` skips archived sessions, and the session is marked archived BEFORE the stop so the stopped turn's end cannot send the next message. After a restore the composer shows "שליחת הבאה", as after a crash.
**Alternatives considered:** (1) Return the queued texts to the composer, as Stop does. (2) Clear the queue.
**Why:** Returning to a composer is wrong: from the sidebar button the open composer belongs to ANOTHER session (the text could be sent to the wrong chat), and after a topbar archive the composer is the welcome page's new-session draft. Clearing loses typed messages silently. Keeping them reuses the "queue waits for a resume" state that already exists, and the stored attachments stay referenced. The cost: the paused queue is only visible after the session is opened or restored.

## [2026-10-27] Archiving asks only when it would stop running background tasks
**Decision:** `actions.archive` shows one confirmation, "להעביר את ... לארכיון?" / "N משימות רקע רצות בסשן, והן ייעצרו.", only when the session has running tasks. Otherwise archiving is immediate, also for a running turn.
**Alternatives considered:** (1) Never ask (the literal "no confirmation" of the request). (2) Always ask. (3) Keep the CLI alive until the tasks end, as the idle timeout does.
**Why:** Archiving is reversible, and stopping a turn is as unconfirmed as Esc. Tasks are the one thing it destroys that the user cannot see going: they live in the CLI process, which archiving closes, and the idle timeout was written never to do that (spec: Background tasks). Always asking is friction on a hover button for the common case; deferring the close would keep a 100-300 MB process for an archived session. The question goes beyond the request's "no confirmation", which is why it is recorded; dropping it is one check in `session-actions.js`.

## [2026-10-27] A session whose folder is gone never starts a CLI (`requireRunnable`)
**Decision:** `requireRunnable(session)` in `lib/session-common.js` answers HTTP 409 with a Hebrew message when `session.cwd` does not exist; `/btw`, control requests and warm-up use it. The git views answer `{ isRepo: false, folderMissing: true, archived }` instead of 400, and the command catalog of such a session is read from `worktree.source`.
**Alternatives considered:** (1) Let the start fail. (2) Restore the worktree automatically on any request.
**Why:** Found by Stage 3 (pass 1): after archiving removed the worktree, `/btw`, control and warm-up spawned the CLI in a folder that does not exist, got ENOENT, and stored a misleading "check claudePath" error item in the transcript. Restoring on every request would make a harmless read (opening a panel) run `git worktree add`; only a message or an explicit restore does. The cost: the same guard now also reports a non-archived session whose folder was deleted by hand ("תיקיית הסשן לא קיימת: ..."), which is a behaviour change for that case.

## [2026-10-27] The archive is a view of the sidebar list; search and the split picker follow it
**Decision:** Archived sessions are filtered out of the normal list, its groups and the split-view picker; "ארכיון (N)" switches the list to them (one group, by `archivedAt`, no grouping switch, restore button per row), and the search covers the list shown. The view is in page memory only. Archived sessions stay in `state.sessions`, so the worktree-delete fork check, the "שיחות קודמות" duplicate check and search still see them.
**Alternatives considered:** (1) Search finds archived sessions in both views. (2) Remember the archive view per browser. (3) Offer archived sessions in the split picker. (4) Remove archived sessions from the browser's state.
**Why:** One rule, "the search covers the list shown", needs no second result style. A remembered archive view would open a stale-looking sidebar after a reload. The split pane's mini composer would restore a session silently, without the banner chip. Dropping them from state would break the fork check (a fork that is archived still needs its folder) and let an archived conversation be imported a second time. The cost: a search in the normal view cannot find an archived chat (an optional "found in the archive" hint was not built).

## [2026-10-27] The GUI creates the session's worktree itself with git, not with `claude --worktree`
**Decision:** `lib/git/worktree.js` runs `git worktree add -b worktree-<slug> <repo>/.claude/worktrees/<slug> HEAD` through the safe git runner, before the session (and its CLI) exists, and the session then runs in that folder. The layout (`.claude/worktrees/<name>`) and the branch prefix (`worktree-`) are those of the CLI's `--worktree`.
**Alternatives considered:** (1) Start the CLI with `-w, --worktree [name]` and let it create the worktree. (2) Branch names with a Desktop-like `claude/` prefix. (3) A name taken from the session name or the first message.
**Why:** The 2.1.246 binary refuses `--worktree` until workspace trust was accepted in an interactive terminal, and this user never opens one. The GUI also has to know the path (rail, chips, removal) before the first message is sent, which a CLI-made worktree would only reveal later. The `worktree-` prefix is what the engine on the user's machine uses, so a later `claude -w` there follows one convention, and it cannot clash with an existing branch named `claude`. The name is ASCII and short (`YYMMDD-xxxx`) because the first message is Hebrew and Windows paths are limited. The cost: the GUI now owns a git write path and must stay in step with the CLI's layout by hand (it did not read Desktop's docs page; a different Desktop prefix would be one constant).

## [2026-10-27] The worktree starts from the chosen folder's local HEAD; nothing is fetched
**Decision:** The base is `HEAD` of the folder the user chose. No `git fetch`, no `origin/<default>`, no network.
**Alternatives considered:** (1) The CLI's default, `origin/<default-branch>` after a fetch (setting `worktree.baseRef` = fresh). (2) `origin/<default-branch>` without a fetch (whatever the last fetch left). (3) Ask the user for a base branch.
**Why:** The machine is closed, and the project documents that the GUI server's only network call is the model-list request, so a fetch (which may also need credentials from the Azure DevOps server) is a new kind of call that was never approved; the user also said plain git, nothing about pull requests. HEAD is the commit and branch the details rail already shows, so the result is predictable, it works in a repository with no remote, and the CLI itself supports it (`baseRef` = head). The cost: it deviates from the CLI default, uncommitted changes and git-ignored files are not in the new worktree (the toggle's tooltip says so), and a stale local branch gives a stale worktree. Changing it later is a localized change plus a spec edit.

## [2026-10-27] The repository's hooks and filters run when the worktree is created
**Decision:** `worktree add` runs the repository's post-checkout hook (also from `core.hooksPath`) and its clean/smudge filters (for example LFS), as the CLI and `git checkout` do. Only fsmonitor stays off (`SAFE_GIT`). The call has a 3-minute limit and closed stdin; a failing hook fails the add and the leftover worktree and its branch are removed.
**Alternatives considered:** (1) Disable hooks (an empty `core.hooksPath`) and filters for this one command. (2) Run the add only after a confirmation that names the hooks.
**Why:** The user asked for a checkout, the programs come from the user's own git config (a clone does not bring hooks), and the project already accepts that a session in a folder loads that folder's Claude hooks without a trust prompt (AGENT_CONTEXT.md, issue 1), a far larger capability. Turning hooks and filters off would break LFS and husky-style repositories and differ from the CLI. The existing rule "repository-configured programs are off" was written for read-only views, where nobody asked git to do anything; ARCHITECTURE.md -> Security now states the exception. The cost: a repository that was copied with a hostile `.git` directory could run code on the first worktree session, which is the same exposure as running `git checkout` in it.

## [2026-10-27] The worktrees are hidden from the main checkout through `.git/info/exclude`
**Decision:** The first worktree appends `/.claude/worktrees/` to `<git-common-dir>/info/exclude` (once, best effort, never failing the creation).
**Alternatives considered:** (1) Do nothing, like the CLI and Desktop, whose docs ask the user to add the folder to `.gitignore`. (2) Edit the tracked `.gitignore`. (3) A global gitignore.
**Why:** Without it every worktree is an untracked entry of the main checkout, so the rail counts it as a new file and the Changes pane says "N קבצים חדשים לא מוצגים": the GUI would look broken. The tracked `.gitignore` would put a change in the user's commits. `info/exclude` is local to the clone, applies to all its worktrees, and is not part of history. The cost: a small write inside `.git` by the GUI, and worktrees made by another tool (a terminal `claude -w`) are not covered.

## [2026-10-27] A worktree session belongs to the folder it was opened from
**Decision:** The session stores `worktree.source` (the folder the user chose) and the UI uses it (`public/js/worktree/project-folder.js`) for grouping by project, the folder line, search, the topbar folder chip and the rail's folder row. The worktree's path and branch are shown separately (branch chip, rail "worktree" row).
**Alternatives considered:** (1) Use `session.cwd` everywhere, so a worktree session is a project of its own named after its slug. (2) Group by the repository root instead of the chosen subfolder.
**Why:** The sidebar spec says "project = the folder"; with `cwd` = the worktree, each parallel session would land in its own group titled `261027-a3f9`, the opposite of why one runs sessions in parallel in one project (how Desktop groups them was not checked; the parity rule and the spec's intent point the same way). The chosen folder, not the root, keeps today's behaviour for a session opened from a subfolder. The cost: `cwd` and the project folder now differ for these sessions, so every new place that shows a folder has to choose (rail, chips and groups already do).

## [2026-10-27] Worktree names and removal are conservative: `-b`, a unique name, no `--force`, the branch stays
**Decision:** The branch is created with `-b` (never `-B`) after the name was checked free as a folder and as a branch; deleting a session asks a second question, "להסיר גם את ה-worktree?", and removal uses `git worktree remove` without `--force` (uncommitted changes keep the folder, with a toast naming the path); the user's actions never delete a branch. The removal target is the path stored on the session, verified under `<root>/.claude/worktrees` and listed by git. A fork shares the worktree, so the question is skipped and the folder kept while another session uses it.
**Alternatives considered:** (1) `-B`, as the CLI does. (2) Always remove the worktree with the session (from memory, Desktop removes it on archive; this was unverified when written and was confirmed from the Desktop docs page in D6, see the first entry above), or never. (3) `--force` after a confirmation. (4) Delete the branch too when it has no unique commits.
**Why:** `-B` resets an existing branch, so a branch kept after an earlier removal could silently lose its commits; `-b` with a checked name makes that impossible. A branch holds the work, a worktree folder is a copy, so only the folder is ever offered for removal, and git's own refusal on uncommitted changes is the safety net, so no force. Asking keeps the choice with the user, and the delete flow was already confirm-based. The cost: removal can leave a folder behind (changes, a Windows lock), and that folder is then listed nowhere in the GUI (the toast names its path); ignored files such as `node_modules` are deleted with the folder, which the question says. `deleteSession` does not wait for the CLI to exit; the lock retry (5 times, 500 ms) covers it, untested on Windows.

## [2026-10-27] Ctrl+\ closes the focused pane; the split view moved to Ctrl+Shift+\
**Decision:** Ctrl+\ calls the pane host's `closeFocused()` (the pane last clicked or focused), as in Claude Code Desktop. The split view toggle is Ctrl+Shift+\. `closeFocused()` was not changed: it does nothing before a pane was clicked or focused, and shows the room-rule toast when the area is hidden.
**Alternatives considered:** (1) Ctrl+\ stays the split toggle and closing a pane gets another key. (2) Leave `closeFocused()` unbound, as D1 shipped it.
**Why:** The user was asked in D4 (the question D1 and the pane-area entry below had left open on purpose) and chose "כמו בדסקטופ", and the standing rule for this batch is to follow the Desktop Code tab as closely as possible. Ctrl+Shift+\ keeps the split on the same physical key, so the tooltip change is the only thing the user has to relearn. The cost: someone used to Ctrl+\ for the split now closes a pane instead (or nothing, before a pane was touched), and the rail is open by default, so the first Ctrl+\ after a page load does nothing until the user clicks in a pane.

## [2026-10-27] Shortcuts are matched by the physical key with exact modifiers
**Decision:** Every page-wide shortcut is a row of the shortcut table with an `event.code` and, where Shift is part of it, `shift: true`. `shortcutFor(event)` needs Ctrl or Cmd, refuses Alt, and compares Shift exactly. A held key is `preventDefault`ed and acts once. Ctrl+K, Ctrl+B, Ctrl+, Ctrl+Shift+O, Ctrl+\ (and the new Ctrl+/ and Ctrl+Shift+\) moved from `event.key` to this.
**Alternatives considered:** (1) Keep `event.key` for the older shortcuts (they did not fire while a Hebrew layout was active: untested deduction in AGENT_CONTEXT). (2) Prefer `event.key` when it is a Latin letter and fall back to `event.code` otherwise, which also suits Dvorak. (3) `event.code` with loose modifiers, as the older handlers were.
**Why:** The user asked for the physical key, and the user types Hebrew: `event.key` is a Hebrew letter there. Exact Shift is needed because two pairs share a key (Ctrl+\ and Ctrl+Shift+\, Ctrl+O and Ctrl+Shift+O); Alt is refused so a layout's AltGr combination (Ctrl+Alt on Windows) never fires a shortcut. Matching by position is also what Ctrl+O and Ctrl+Shift+D already did (see the Ctrl+O entry below). The cost: Ctrl+Shift+K and Ctrl+Shift+B no longer fire (they did); on a non-QWERTY Latin layout the shortcut sits where the key is on a US keyboard, not under the printed letter; on a layout where `/` needs Shift (German) Ctrl+/ is the key that types `/` on a US keyboard. Not tried on a Mac (Cmd).

## [2026-10-27] One table feeds the handler, the Ctrl+/ dialog and the help panel
**Decision:** `public/js/shortcuts/shortcut-list.js` is the only list of shortcuts. `bind-shortcuts.js` (the keydown listener), `shortcuts-dialog.js` (Ctrl+/) and `panels/panel-help.js` (the `/help` section) all read it. Keys handled elsewhere (the composer's Enter, Shift+Enter, `/`, `@`, Shift+Tab, ↑, Esc, and Ctrl+Enter in the Changes pane) are rows without an `action`, listed so the lists are complete.
**Alternatives considered:** (1) Keep the hand-written help list and write a second one for the dialog. (2) One table for the dialog and the help panel, with the handler's keys still hand-written in `shortcuts.js`.
**Why:** The hand-written help list was already stale (it missed Ctrl+O, Ctrl+\ and Ctrl+Shift+D), and two lists plus a handler are three places to edit for one new key. With the handler in the table too, a key can only be added in one way, and the dialog and the help panel follow. The cost: the table's action names are a contract with `app.js`, and the documentation-only rows can drift from the code that really handles those keys (the composer, the Changes pane), because nothing ties them together.

## [2026-10-27] Tool groups wrap the existing rows in the DOM; a lone tool row is not grouped
**Decision:** In Normal and Thinking, `tool-groups.js` wraps a run of two or more consecutive top-level `details.tool` rows in a `details.tool-group` (summary: "N כלים", verbs ×N, state icon). The rows keep their nodes, ids and listeners. Live items extend the last group (`groupAppended`); a mode change regroups the whole thread. A single tool row stays a plain row.
**Alternatives considered:** (1) Re-render the thread from `session.items` for each mode, building groups at render time. (2) CSS only (hide rows, no summary line). (3) Group inside `appendItem` while building nodes. (4) Group even a single call.
**Why:** The rest of the thread finds tool rows by `data-tool-id` (results arrive later, subagent rows nest inside their parent), search finds items by `data-item-index`, and the file-viewer and copy buttons use delegated listeners; moving the existing nodes keeps all of that working and leaves `thread.js` and `render-*.js` almost untouched. CSS alone cannot produce a counted, verb-listing summary. A summary of one call adds a line and a click for nothing, and the row already is a closed one-line summary. The cost: the thread is regrouped as a whole on each mode change and session show (unmeasured on very long sessions), and any node between two rows (text, notice, todo card, visible thinking) ends a run.

## [2026-10-27] `/focus` stays a separate filter; it is not mapped onto the view modes
**Decision:** `/focus` (the `focus-view` body class) is unchanged. It hides tool rows, thinking and notices in any mode, and `transcript.css` makes it hide the new groups too.
**Alternatives considered:** (1) Make `/focus` a fourth view mode, or an alias of one of the three. (2) Remove it in favour of the modes.
**Why:** Nothing in spec.md defines focus view except that the per-turn changed-files card stays visible in it, so keeping it needs no spec change, while mapping it would have changed that line and the status panel text. It differs from every mode: it is global (a body class), also hides notices, and is not remembered per session. The Desktop text quoted for this feature describes the three transcript modes only, so merging would have given up existing, tested behaviour without a clear parity gain. The cost: two ways to see less.

## [2026-10-27] The view mode is per session; each thread applies its own session's mode, controls act on the main thread
**Decision:** The mode is saved per session in this browser (`claude-gui.transcript-view`). The main thread and the split pane each have their own transcript view and apply the mode of the session they show. Ctrl+O and the "עוד" menu section change the main session only; the pane has no control.
**Alternatives considered:** (1) One global mode for the whole page. (2) Controls in the split pane's header. (3) The split pane always shows everything (Verbose).
**Why:** The user asked for a per-session view like Desktop's. Both threads come from `createThread`, so a per-thread view is the natural unit and two sessions can differ without extra state. Pane controls would add header UI for something rarely changed there, and `/btw`, the search bar and the workspace panes are already main-only; swapping a session into the main pane reaches the controls. The cost: a pane session's mode can only be changed by swapping it in.

## [2026-10-27] Ctrl+O is a global shortcut matched by the physical key
**Decision:** Ctrl+O (or Cmd+O) cycles the view mode from anywhere on the page, including the composer, using `event.code === 'KeyO'`. It is ignored with Shift or Alt, a held key cycles once, and it always calls `preventDefault`.
**Alternatives considered:** (1) Only outside text fields. (2) `event.key`, like Ctrl+K and Ctrl+B. (3) Leave it out and offer the menu only.
**Why:** Desktop binds Ctrl+O globally, and the other page-wide shortcuts here already work inside the composer; Ctrl+O has no text-editing meaning on Windows. `event.key` reports a Hebrew letter on a Hebrew layout, so the shortcut would not fire there (the user types Hebrew); `event.code` is the same key on any layout, as Ctrl+Shift+D already does. `preventDefault` stops the browser's "open file" dialog. Ctrl+Shift+O stays "new session". The cost: the older letter shortcuts still use `event.key` until D4 (D4 moved them: see "Shortcuts are matched by the physical key with exact modifiers" above).

## [2026-10-27] The Changes pane has its own route; untracked files are synthesized in node
**Decision:** `GET /api/sessions/:id/diff` (lib/git/session-diff.js) returns one text: `git diff` against HEAD for the whole repository, followed by every untracked file (`git ls-files --others --exclude-standard`) written as a "new file" diff that adds all its lines. The new-file diffs are built in node with limits: at most 100 files, 512 KB each, 2 MB read per request, `lstat` so symlinks are skipped, binary (NUL in the first 8 KB) and empty files handled; skipped files are counted (`newFilesSkipped`).
**Alternatives considered:** (1) Reuse `/api/git` (`gitChanges`) as it is. (2) `git diff --no-index -- /dev/null <file>` for each untracked file. (3) `git add -N` (intent to add) so git itself lists them. (4) Show untracked files by name only, with no diff (descope).
**Why:** `gitChanges` has no untracked files, and Claude often creates new files, so a pane without them would miss part of what a reviewer wants to comment on (the rail already counts them as files). `git add -N` changes the user's index, which a read-only view must never do. A name without lines allows no line comments. `--no-index` was the closest alternative: it needs one git process per file, and its exit code 1 means "differences found", which the shared `git()` helper reports as a failure. Building the text in node keeps the limits (count, size, symlinks, binary) in one place and produces the same format the one parser (`diff-parse.js`) already reads. The cost: the synthesized text is not byte-identical to git's (mode always `100644`, no "\ No newline at end of file" line, a non-UTF-8 file is decoded as UTF-8), and the route reads file contents beyond the session folder (documented in ARCHITECTURE.md -> Security).

## [2026-10-27] The pane diffs the whole repository against HEAD; the /diff panel keeps staged and unstaged apart
**Decision:** The Changes pane shows each file once, as its net change from HEAD (staged and unstaged merged), for the whole repository from its top level. The settings-modal git panel (`/diff`, `/api/git`) is unchanged: staged then unstaged, so a file can appear twice there.
**Alternatives considered:** (1) The pane uses the same staged + unstaged text as `/diff`. (2) Only the session folder (a pathspec of `.`). (3) Switch `/diff` to the new route too.
**Why:** A comment is anchored by file path, side and line, so the same path appearing twice would make the anchor ambiguous; one diff per file is also the natural unit to review file by file. The whole repository, because the rail's counts already come from git commands without a path and a session started in a subfolder would otherwise hide changes the rail counts. Leaving `/diff` alone keeps an existing, tested screen as it was and was not part of this feature. The cost: the rail's counts (numstat; untracked files as files only) and the pane's toolbar counts (new files' lines included) can differ, and the pane reads more than the session folder.

## [2026-10-27] Line comments are anchored by path, side, line and text, and are never dropped silently
**Decision:** A comment keeps `{ path, side, line, quote }` (the line's text when written). It shows under its line only while the line still has the same number and text; otherwise it moves to "הערות על שורות שהשתנו מאז" under its file, or (file gone from the diff) to a list at the top. Such comments stay deletable and are still sent. Comments are cleared only after a successful send.
**Alternatives considered:** (1) Anchor by line number only. (2) Drop comments whose line changed at the refresh after a turn. (3) Clear all comments on every refresh.
**Why:** The pane refreshes when a turn ends, and Claude's edits shift line numbers, so a number-only anchor would put a comment on the wrong code, while dropping would lose what the user wrote before they sent it. Comparing the text as well keeps a comment on its line only when it is still about that line; the message sent to Claude quotes the line, so a moved comment still says what it was about. The cost: a comment on a line that was only reindented shows under "changed since" instead of in place.

## [2026-10-27] The pane area belongs to the main session only and is hidden by a room rule
**Decision:** The workspace panes and the session details rail are shown for the main (active) session only. The area appears only when the workspace row has at least 560 px for the chat plus the column's width; otherwise it is hidden, the saved choice is kept, and the toggle only shows a toast. There is no special case for the split view: it narrows the main region, so the same rule hides the area. Open panes and the width are global per browser, not per session.
**Alternatives considered:** (1) Panes for both the main and the split session. (2) Opening a pane closes the split view (or the reverse). (3) Per-session open panes. (4) A viewport media query instead of measuring the row.
**Why:** Desktop panes belong to the focused session, and `/btw` and the search bar are already main-only, so the user's mental model stays consistent. At the split view's 1000 px minimum the main region is about 360 px, so the chat would be squeezed under both a rail and a split pane; a rule on the real row width covers this and every other narrow case (collapsed or open sidebar, any window size) with one check and no coupling between the two features. Keeping the saved choice (and not changing it on a toggle without room) means a narrow window never loses the user's layout. The cost: on a very wide window the area can sit next to the split pane, which was judged acceptable. Ctrl+\ was left untouched on purpose (a pending question for D4); D4 answered it: see the entry "Ctrl+\ closes the focused pane" above.

## [2026-10-27] The rail's change totals come from a small `git-summary` route, not from `/api/git`
**Decision:** `GET /api/sessions/:id/git-summary` (lib/git/changes.js `gitSummary`) returns `{ isRepo, branch, files, untracked, added, removed }` from `git status --branch` plus `git diff --numstat` (staged + unstaged). It takes the folder from the session on the server and has no `cwd` parameter. The git runner and its safety flags moved to lib/git/run.js so both git views share them.
**Alternatives considered:** (1) Reuse `/api/git` and count `+`/`-` lines of the returned diff in the browser. (2) Add the summary to `lib/workspace-info.js`. (3) Count what Claude's edit tools wrote (as the per-turn card does) instead of asking git. (4) Count the lines of untracked files.
**Why:** `/api/git` returns up to 300000 characters of diff and cuts it, so counts from it would be wrong for big changes and heavy to fetch on every turn; numstat gives exact totals in a few bytes. `workspace-info.js` was already at the size budget and git is a separate topic (one folder per feature), and moving the runner keeps the safety flags in one file. Asking git covers Bash-made changes that the edit-tool view misses, at the price that the card shows the folder's uncommitted changes, including ones not made in this session (said in its tooltip and the spec). Untracked files are counted as files, not lines, because reading every new file would be unbounded work for a card that refreshes on each turn.

## [2026-10-27] The file viewer reads the file's current text through a session-scoped route
**Decision:** `GET /api/file-view?sessionId=&path=` (lib/file-view.js) returns the file as it is now. The allowed roots (session folder, `addDirs`, uploads) are taken from the session on the server, compared as real paths, and any `cwd` parameter is ignored.
**Alternatives considered:** (1) Show the content recorded in the tool item (Read result, Edit strings) with no new route. (2) A route taking `cwd=` or any absolute path. (3) A general "read any file" route.
**Why:** The recorded tool content is partial (Edit holds only the changed strings, Read results may be cut) and cannot show surrounding lines or highlight a line range. A request-supplied `cwd` or free path would make the folder check meaningless and turn the route into an arbitrary-file reader, which the no-auth, cross-site-GET issues make worse. Session-scoped roots limit it to the places Claude already works in without asking. The cost is that the view can differ from what the tool saw if the file changed since; marks are then simply omitted.

## [2026-10-27] Prompt templates are stored on the server, not in localStorage
**Decision:** Templates live in `data/templates.json` (lib/templates.js) behind `GET /api/templates`, `PUT/DELETE /api/templates/:id`; the browser generates the id and PUT upserts.
**Alternatives considered:** Per-browser localStorage (like the notification and sidebar-grouping preferences).
**Why:** Templates are user content worth keeping, not a display preference. The server file survives a browser reset or cleared site data and every tab sees the same list. The cost is a new route set and a data file, kept small by limits (name 80, text 20000, 200 templates) and an atomic write like the session store.

## [2026-10-27] /btw gets its own route, not the generic control whitelist
**Decision:** `POST /api/sessions/:id/side-question` (lib/side-questions.js) sends the `side_question` control request with a 10 minute timeout.
**Alternatives considered:** Add `side_question` to `WRITE_SUBTYPES` in lib/catalog-service.js and use the generic `/control` route.
**Why:** The generic control routes are documented as costing no tokens and have short default timeouts; `side_question` calls the model and the local model can be slow. A separate route keeps that guarantee true and allows input limits (question 4000 characters, history 20).

## [2026-10-27] Session search runs in the browser, no server index
**Decision:** Full-text search scans `session.items` in the browser (public/js/session-search.js), newest 3000 items per session, count capped at 99.
**Alternatives considered:** A server-side search endpoint or index over `data/sessions.json`.
**Why:** `/api/state` and SSE already give the browser every item, so no new route, no index to keep in sync with live streaming, and results stay current as items arrive. The cost is a scan per query, bounded by the cap and a 150 ms debounce.

## [2026-10-27] The split-view pane has a mini composer, and extras stay main-only
**Decision:** The second pane has a live thread, its approval cards and a compact composer (text, send, stop). Attachments, slash menus, `@`, chips and `/btw` stay in the main composer; a swap button makes the pane's session the main one.
**Alternatives considered:** A read-only second pane; a full second composer with every feature.
**Why:** The use case (one session plans, another executes) needs sending to both, so read-only is not enough. A full second composer would duplicate menus, attachments and commands that are wired to the single active session, for little gain; one-click swap covers them.
