# Decisions

## [2026-10-30] Prompt templates are the user's CLI custom commands: ASCII command name in the form, CLI-native arguments in the file, every user command is a template
**Decision:** A template is one file `<config home>/commands/<name>.md` (user scope, honors `CLAUDE_CONFIG_DIR`); `lib/templates/` (`template-store.js`, `command-format.js`, `template-migration.js`) replaced `lib/templates.js` and `data/templates.json`. (A) The panel form has a required field "שם הפקודה בטרמינל" (ASCII, `NAME_PATTERN`), prefilled from the Latin letters of the name; the Hebrew name is the front matter `description`. (B) Variables are written in the CLI's own form: `$1`…`$9` (a single variable `$ARGUMENTS`) plus `argument-hint: [name1] [name2]`; the editor still shows and accepts `{{name}}` and converts on save and open; more than 9 variables are refused. (C) Every file directly in the user commands folder is a template, also the ones written in the terminal; one the CLI expands (an inline `!` with a backtick command, or a line starting with `@`) inserts `/name ` instead of its body. Saving keeps other front matter keys, quotes the values, and drops a BOM / writes LF. Startup moves a leftover `data/templates.json` into files (slug, `slug-2`, … or `template-N`; mtime = old `updatedAt`; never overwrites; renamed `.migrated`, never deleted). PUT is `{ description, text, create, previous }` (create 409 when taken, rename when `previous` differs). No `reload_skills` after a save.
**Alternatives considered:** (A) a generated name `template-1` the user never sees (the terminal then has commands nobody can remember); widening `NAME_PATTERN` to Hebrew (rejected: it is a security boundary of Claude's files, changed only by a spec decision). (B) keep `{{name}}` in the file (the GUI form works, but the terminal's `/name` sends `{{name}}` literally); show raw `$1` in the editor. (C) only files the GUI created, marked with a non-standard key (the terminal's commands would stay out of the list). A single variable as `$1` instead of `$ARGUMENTS` (Stage 2 chose `$ARGUMENTS`, which the CLI fills with everything typed after the command, so a value with spaces works in the terminal too). Calling `reload_skills` after each save.
**Why:** The developer's decision of 2026-10-29 ("prompt templates become CLI custom commands, so the terminal has them too") applied the rule that the CLI is the source of truth; the three details were asked of the user (AskUserQuestion, Hebrew) after Stage 1 and each time the recommended option was chosen. This replaces the storage of the entry of 2026-10-27. The costs, accepted: a command name must be ASCII; `$1` and a literal "$1" in the text are the same thing; a value with spaces works only in the GUI for `$1`…`$9`; a running session's "/" menu may show a new template only after its process restarts. UNVERIFIED: the real CLI's expansion of `$1`/`$2`, of a repeated `$1`, and of a non-ASCII `argument-hint` (a real expansion needs a model call and the user declined paid tests); the GUI fills the arguments itself, so the GUI path does not depend on it. Verified by a verify-agent against the fake CLI (second round after a BOM-prefixed file corrupted on edit and an empty command field sent `PUT /api/templates/`; both fixed).

## [2026-10-30] Cost comes from the CLI: a turn's cost is the growth of its `get_usage` total; the GUI keeps no session total
**Decision:** A turn's `costUsd` is how much the CLI's running total for the process (`get_usage` `session.total_cost_usd`) grew during the turn (`lib/runtime-cost.js`: a baseline after `initialize`, a reading after each result, 2 s at most each). When a reading is missing the turn takes the result's `total_cost_usd`; a result without one gets `null` (unknown, never 0). The GUI no longer sums or stores a session cost (`session.costUsd` is gone from `onItem` and the store; old stored values stay in `sessions.json`, unused). The usage panel shows only the CLI's figures for the current process ("עלות לפי ה-CLI (התהליך הנוכחי)", API time, lines added / removed) with a note that the figure restarts with each new CLI process, plus the `get_session_cost` text. Built the same day as the decision of 2026-10-29.
**Alternatives considered:** (1) Keep the GUI's session total and show it next to the CLI's figure, labelled (what Stage 1 recommended). (2) Take the delta of the result's own `total_cost_usd` (`total - last seen`, else `total`): it cannot tell a per-turn CLI from a running-total one (per-turn costs 0.01 then 0.03 would give 0.02, equal costs 0), so Stage 1 rejected it. (3) Use the result's `total_cost_usd` as the turn's cost, as before (over-counts when it is a running total). (4) Test per turn vs running total with a paid call (the user declined and said to build without testing).
**Why:** The user was asked (AskUserQuestion, Hebrew) after Stage 1 found "cost comes from the CLI, not from the GUI's sum" ambiguous, and chose "רק מה שה-CLI מדווח" over keeping both. The cost of that choice, accepted: there is no cost total for a conversation across CLI restarts (idle, settings, resume); each process starts again, and the panel says so. `get_usage` is the one figure whose meaning is known (a process total, shape checked on CLI 2.1.181 with no model call), so the per-turn figure does not depend on the unverified question. UNVERIFIED: whether a result's `total_cost_usd` is per turn or a running total; it is used only when `get_usage` fails or is absent, and as a running total it would overstate that turn. The CLI may restore an earlier total on `--resume`; the baseline covers that. A stopped turn's result is swallowed into the "הריצה הופסקה." notice (as before), so its cost is not shown, but its reading becomes the next baseline. Verified by a verify-agent against the fake CLI only (several turns per process, idle and settings restart, adopted spare, stopped and held turns, queue order, `get_usage` never answering); not against the real CLI.

## [2026-10-30] A turn another program ran gets a result item built from the CLI's file
**Decision:** The CLI writes no `result` line to its `.jsonl`, so a turn run in a terminal (`claude --resume`) had no stats line and no changed-files card. `lib/transcripts/turn-results.js` now builds a `result` item (`fromFile: true`) for such a turn while the history is built (not stored, not an extra, not through `onItem`): time from the typed message to the turn's last message, tokens summed over the last line of each distinct `message.id`, rounds = the number of ids, `durationApiMs` 0, `costUsd` null. Only a turn whose typed line's `entrypoint` is not `claude-code-gui` and where the GUI holds no `result` extra on any line of the turn; the last turn only when its final answer has `stop_reason: 'end_turn'`. The tooltip says "מחושב מקובץ השיחה (הרצה מחוץ ל-GUI), ללא עלות".
**Alternatives considered:** (1) Leave the gap (the state before). (2) Only the changed-files card, no stats line. (3) Give any turn without a `result` item one (a GUI turn that was stopped or failed has none, and would show a false "success" line). (4) Store the derived result as an extra when first seen (a second copy that can drift from the file).
**Why:** The developer listed it as an open follow-up of the history move and asked for the open tasks to be built; the spec already says each finished turn shows its stats. The time between the typed message and the last message has the same meaning as the CLI's `duration_ms` (it includes waiting for an approval); there is no model time and no cost in the file, so the line shows neither. **Departure from the CLI, flagged:** the GUI derives a result the CLI does not write, and its numbers are the file's, not the CLI's own. Decided in Stage 1 without asking the user. It does not touch the planned change "cost comes from the CLI": the item never feeds `session.costUsd`, and a later cost task must read a `null` per-turn cost as unknown, never 0. Known limits: subagents' tokens are not counted; an interrupted terminal turn followed by another prompt looks like a finished one; an interrupted last turn gets none.

## [2026-10-30] Extras that can never show again are deleted, conservatively
**Decision:** After each build `refresh` deletes from `session.extras` (and so from `sessions.json`) the ones for which no anchor is on a shown chain and every anchor is a line of the files read (`lib/history-prune.js`). Nothing is deleted when a conversation file is missing, `resumeAt` or `forkPending` is set, or the session has no current conversation; an extra with no anchors, or with an anchor no file holds, stays.
**Alternatives considered:** (1) Keep them all (they only accumulate, small). (2) Delete every extra with no anchor on a shown chain (loses items of a CLI that is still writing, and of a file that was deleted and may come back). (3) Mark instead of delete (a state that must be kept in step with the files).
**Why:** The developer asked for it (follow-up of the history move). A terminal `/rewind` leaves the GUI's results and notices of the abandoned part behind; they could never show again. Deleting is final, so the rule needs proof the lines exist and are off the chain. Accepted risk: if the CLI ever writes a compaction boundary without `logicalParentUuid`, the history before it would not be on the chain and its extras would be deleted although a later reader might show it. The prune only affects extras; `session.sent` also keeps entries for lines that no longer show and is not pruned yet. Decided in Stage 1 without asking the user.

## [2026-10-30] The CLI files are read incrementally with a bounded cache; `transcripts.js` is split in a folder
**Decision:** `lib/transcripts/jsonl-reader.js` `readLines(file)` keeps per file the parsed lines up to the last newline read, that offset and the 64 bytes before it; when the file is not smaller and those bytes are unchanged only the new bytes are read, else the whole file. A last line with no newline yet is returned but not kept. The cache holds at most 32 MB of files (least recently read out first); a larger file is read whole every time. Callers get a new array but share the line objects (nobody may change them). `lib/transcripts.js` (256 lines) became `lib/transcripts/` (`transcript-files.js`, `transcript-items.js`, `turn-results.js`, `jsonl-reader.js`); `require('./transcripts')` no longer resolves, the callers name the file.
**Alternatives considered:** (1) Keep reading the whole file on every build (the state before; with the one-second look and a 24 MB file each change cost a full parse). (2) A cache bounded by the number of files (a few very large conversations could use a lot of memory). (3) Compare the modification time and size only (an in-place rewrite of the same size is missed too, and mtime is unreliable on Windows). (4) A `lib/transcripts/index.js` that hides the split (no: `./transcripts` would silently pick a leftover `transcripts.js`).
**Why:** The developer listed "read only the end of a large file when it only grew" as a follow-up of the history move, and the split follows the spec's rule that code is separated by feature (code-standards rule 1; the file was over the ~150-line budget). Measured by the verify pass: a 24 MB file, 48 ms first read, 2.7 ms incremental, about 26 MB of heap. Known limit: only the 64 bytes before the cached end are compared, so a same-size in-place rewrite that keeps those bytes is not seen (the CLI only appends). Decided in Stage 1 without asking the user.

## [2026-10-30] Credentials in `ANTHROPIC_BASE_URL` are dropped, not turned into a Basic auth header
**Decision:** The model list, the health dot and the startup log use `displayUrl(baseUrl)` (no user, password or query; '' unless the protocol is http or https). The user:password of the URL is not sent anywhere; `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_API_KEY` stay the only auth of the GUI's own request. The error text never contains the raw URL (also any raw-URL occurrence in a failure message is replaced).
**Alternatives considered:** (1) Turn `user:password@` into an `Authorization: Basic` header so a proxy that needs it answers the list. (2) Leave the list failing as it did.
**Why:** The health dot already did (1)'s opposite (dropped them) and the spec says the two use the same request. A Basic header would be a new feature that handles the password. Cost: a proxy that really needs URL credentials answers 401 to the GUI's list and dot (shown as the error, the configured names still appear), while Claude Code's own turns are not touched. Decided in Stage 1 without asking the user. The check found that a base without a scheme (`user:secret@host:11434/v1`) parses as an opaque URL with protocol `user:` and leaked, hence the http(s)-only rule: such a base is "invalid" (list error "ANTHROPIC_BASE_URL אינה כתובת תקינה", health dot down with that text, startup log "(invalid URL)").

## [2026-10-30] `model`, `agent`, `effort` and `outputStyle` are checked on the request paths only
**Decision:** `checkText(key, value)` in `lib/session-options.js`: `model` and `agent` match the `fallbackModel` pattern `MODEL_ID`; `effort` is `''` or `low|medium|high|xhigh|max`; `outputStyle` is up to 128 characters with no control characters. Used by `textChanges` (PATCH), `startSession` and the draft branch of `warm`; a bad value is 400 with a Hebrew message. `createSession` (fork, import) does not check. The chip menu's model and effort buttons show the refusal as a toast (`actions.trySettings`).
**Alternatives considered:** (1) Check in `createSession` too (a session saved before this change with an odd model could not be forked). (2) A looser pattern for `model` that allows a leading `/` or spaces (the vLLM path-style ids would be pickable, but `%`, a leading dash and cmd.exe metacharacters would need their own rules). (3) A leading-dash rule for `outputStyle` (dropped: it only goes into a JSON file, so it has no safety basis). (4) Read the allowed effort levels from the CLI (the CLI is the source of truth, but the GUI only offers the five levels of `EFFORT_LEVELS`, so a list synced by hand is enough).
**Why:** `model` and `agent` go into argv through the Windows `.cmd` shim, where `%` and a leading dash are a problem; D14 already did this for `fallbackModel`. Narrowing "a free name" is the price: a name the model server lists but the pattern refuses is refused when picked (use `model` in `config.json`, which is not checked). Decided in Stage 1 without asking the user. Not done: re-validating stored values at CLI start.

Status: decided; cost built 2026-10-30 (see the entry "Cost comes from the CLI": the developer chose to show only the CLI's figure); prompt templates built 2026-10-30 (see the entry "Prompt templates are the user's CLI custom commands"); the rest not built yet.

## [2026-10-29] Session settings are per platform: the GUI keeps its own, a terminal run of the same conversation keeps its own
**Decision:** The session settings the GUI stores and passes to the CLI on each start (permission mode, model, effort, agent, extra folders, output style, fallback model, thinking off, custom system prompt, safe mode) stay the GUI's. They are not written into the CLI's conversation or settings files and not read back from a terminal run, except the permission mode the CLI reports live (`onModeChange`). A conversation continued in a terminal (`claude --resume`) runs with that terminal's flags and the CLI's own settings, and the GUI's settings apply again when the GUI starts its process. Listed under "Departures from the CLI" in ARCHITECTURE.md as accepted, not as an open gap.
**Alternatives considered:** (1) Store them in the CLI conversation so both sides share them: the CLI has no place for most of them in the `.jsonl`, and writing one would invent a CLI format. (2) Write them to the project's `.claude/settings.local.json`: that would change every conversation in the folder, terminal ones included. (3) Read the terminal's choice back: the CLI does not record most of them in the conversation file (UNVERIFIED per setting).
**Why:** The developer's decision: these are run settings that can be changed at any point in a conversation, not part of the conversation itself, so a different value per platform is expected and is not a second truth. In the CLI too they are per run: flags at start, and the mode, model and effort change live in the middle of a conversation (`/model`, Shift+Tab). The conversation itself (history, name) stays the CLI's alone.

## [2026-10-29] The conversation shown is built from the CLI's file; the GUI keeps only what the file does not hold
**Decision:** `data/sessions.json` no longer holds a session's items. `session.items` is built in memory from the CLI's `<config>/projects/<folder>/<id>.jsonl` (the conversations before each `/clear`, then the current one): the chain from the file's latest line back through `parentUuid` and through compaction boundaries (`logicalParentUuid`), or from `resumeAt` after a GUI rewind. The GUI keeps only what the file does not hold, as `extras` placed after the uuid of a CLI line (turn results, notices, errors, dividers, `!` output), and how it showed the messages it sent (`sent`, used only while the CLI's line holds that exact text). The files are looked at every second and read when one changed; a different build is sent to the browsers as a `history` event. A change written by another program closes the session's idle process. GUI rewind, fork, `/clear` and import change only what the CLI is told and which conversations are shown. The fake CLI writes a transcript too. Code: `lib/session-cli-sync.js`, `lib/history-build.js`, `lib/transcripts/` (was `lib/transcripts.js` until 2026-10-30).
**Alternatives considered:** (1) Keep the GUI's copy and append what a terminal adds (the step before, same day): a terminal rewind or compaction could not be shown, and two copies drift. (2) `fs.watch` instead of a one-second look: unreliable across platforms and editors that replace files. (3) Store GUI-only items in the CLI's file: it is the CLI's format, and the CLI would read them as conversation. (4) Rebuild only on page load: an open page would not show terminal changes.
**Why:** The developer asked for the GUI to take the conversation from the CLI, to show terminal changes without delay, and to handle a rewind and a compaction made in the terminal. Checked on 2.1.312 with real turns: uuids the GUI sends become the line uuids, `--fork-session` keeps them, a terminal rewind starts a new branch from the chosen point (nothing is written before the next message), a compaction writes a boundary with `logicalParentUuid`, and `--resume-session-at` refuses an answer before the last compaction (those messages are therefore not rewind points). **Departures from the CLI, flagged:** the GUI's own items (results, `!` output, dividers) have no place in the CLI and stay in `sessions.json`; the GUI shows the history before a compaction (the CLI's terminal shows the summary). Subagent steps are read from the CLI's own subagent files (`<conversation>/subagents/`), added after a verify pass found them missing after a rebuild. Sessions from before this change were not migrated (the tool is in development).

## [2026-10-29] A GUI session is a CLI conversation that `claude --resume` lists under the same name
**Decision:** (1) Every CLI process the GUI starts gets `CLAUDE_CODE_ENTRYPOINT=claude-code-gui` (`lib/session-env.js`; `config.json` `env` can still override it). (2) A name a person gives (rename, `/rename`, a fork's "(ענף)") goes into the CLI conversation: through the running process with the control request `rename_session` (`{ title, source: 'host' }`, the one the Agent SDK's `renameSession` sends), otherwise by appending the line the CLI's own /rename writes (`{"type":"custom-title","customTitle":…,"sessionId":…}`) to the `.jsonl`. A new CLI conversation of the same session (first message, `/clear`, fork) gets it when the CLI reports its id. (3) The other way: when the browser loads the list and at every turn end, the GUI reads the CLI file (only when its mtime changed) and takes a name given in a terminal, the CLI's own title for a session nobody named (`ai-title`, else a summary, else the first prompt: what the picker shows), and answers a terminal added after the GUI's last known answer (`lastAssistantUuid`, followed by `parentUuid`, only lines another program wrote); those are appended after the divider "המשך השיחה מחוץ ל-GUI (טרמינל)" and the session's idle process is closed, so the next message resumes from the file. Code: `lib/session-cli-sync.js`, `lib/transcripts/transcript-files.js` (was `lib/transcripts.js` until 2026-10-30).
**Alternatives considered:** (1) `--name` on the command line (exists on 2.1.312): only at a process start, so a rename of a running session would need a restart, and a spare process warmed before the session existed would have none. (2) `CLAUDE_CODE_ENTRYPOINT=claude-vscode` or `claude-desktop`, which the picker also lists: it would tell the CLI (and its telemetry) that the GUI is another product. (3) Re-importing the whole conversation from the file on every change: it would drop GUI-only items (`!` output, dividers, the history before a `/clear`). (4) The full move of the history to the CLI file (AGENT_CONTEXT.md -> Next Steps): still the goal, larger.
**Why:** The developer asked that every GUI session really be kept by the CLI and appear in the same `/resume` list with the same name. Checked on 2.1.312 with real turns: `claude -p` in stream-json mode does write the `.jsonl`, but marks it `entrypoint: "sdk-cli"`, and the picker hides `sdk-*` conversations (`sdk-cli`, `sdk-ts`) while it lists `claude-vscode`, `claude-desktop`, `local-agent` and an unknown value such as `claude-code-gui`; the CLI keeps any `CLAUDE_CODE_ENTRYPOINT` except `cli`, which `-p` turns into `sdk-cli`. **Departures from the CLI, flagged per the rule above:** `claude-code-gui` is a value the CLI does not document (it is treated like an unknown client; the picker filter is not a documented interface and can change); appending a `custom-title` line writes into the CLI's own file (the same line its /rename writes, used only when no process holds the conversation or the CLI refuses `rename_session`, e.g. older versions). Not covered: conversations the GUI started before this change keep `sdk-cli` and stay hidden in the picker (`claude --resume <id or name>` still opens them); 2.1.246 was not checked (`rename_session` falls back to the file line there).

## [2026-10-29] The CLI is the brain and the source of truth; the GUI is a display, and any departure is flagged to the developer
**Decision:** The Claude Code CLI owns the conversation: its history (the `~/.claude/projects/<folder>/<id>.jsonl` transcript, read through `--resume`), its commands, tools, permissions and settings. The GUI renders what the CLI says and sends what the user asks; it keeps only what the CLI has no place for (pins, archive, templates, split view, notification settings, the message queue, the worktree link, GUI-only items such as `!` shell output, GUI-only session color). Where the CLI already has a feature the GUI follows the CLI's behaviour, flags and names and does not reimplement it. A feature that cannot be built without departing from the CLI (a second copy of the history, a GUI-side substitute for a CLI behaviour, an invented flag or control request, a change the CLI would not accept) must not be decided silently: the developer states it in the invocation reply and in the entry of that feature in this file, with the reason and what would be needed in the CLI instead.
**Alternatives considered:** (1) Keep the GUI's own copy of the history in `data/sessions.json` as the source for display and search (the state before this entry). (2) Make the GUI the source and write back to the CLI's files. (3) A mirror of both with periodic sync.
**Why:** Two histories drift apart: the GUI list did not match `/resume`, a session could not be continued from the terminal with the same view, and `--resume` silently loses context when the CLI's file is missing while the GUI still shows the whole conversation. One source removes the drift, makes a terminal session and a GUI session the same thing, and keeps the GUI honest about what the model really sees. Cost: the GUI depends on the CLI's undocumented `.jsonl` format and on `--resume`, so that reading must live in one layer with tests, and GUI-only items need a side file keyed to a CLI uuid. Status: the rule for all new work; the history move was done the same day (entry "The conversation shown is built from the CLI's file").

## [2026-10-29] Safe mode means "a person always approves": it forbids `bypassPermissions` and `auto`, nothing else
**Decision:** The per-session switch "מצב בטוח" (D16) refuses the permission modes `bypassPermissions` and `auto` on the server (`updateSession`, the plan card's `setMode`; `requireMode(mode, safe)`) and hides them in the GUI (chip menu, permissions panel, Shift+Tab cycle). `dontAsk` stays allowed (it only denies). Turning safe mode on in a forbidden mode switches the session to `default` in the same PATCH. No `--disallowedTools` list. The user's `!` shell and the file editor are not limited, and a mode change reported by the CLI itself is shown, not blocked.
**Alternatives considered:** (1) Also pass `--disallowedTools` for the riskiest tools (Bash, WebFetch, WebSearch, destructive patterns). (2) A 400 when turning it on in a forbidden mode instead of switching. (3) Blocking the CLI-reported mode change by sending `set_permission_mode` back. (4) Making it a sandbox (also limiting `!` and the editor).
**Why:** The request said "decide a concrete, honest meaning from what the CLI supports, smallest useful, safe and verifiable". Mode choice is something the GUI controls end to end and can be tested against the fake CLI; a tool-rule syntax cannot be verified without the real CLI and would suggest protection that may not exist. Switching to `default` avoids a dead-end error and is shown in the panel. Naming the limits (CLI-reported change, `!`, editor) in the spec keeps the switch from being read as a sandbox. `optionArgs` is the extension point if a tool list is wanted later.

## [2026-10-29] The custom system prompt travels only as a file, with a file flag that `--help` must list
**Decision:** The prompt text is written to `<data>/session-settings/<id>.system-prompt.md` and passed as `--append-system-prompt-file` (default, mode append) or `--system-prompt-file` (mode replace), only when `claude --help` lists that flag. If it does not, the panel shows a disabled note and nothing is passed (no argv fallback). Up to 20,000 characters, no NUL. Removed on session delete, kept on archive.
**Alternatives considered:** (1) `--system-prompt` / `--append-system-prompt` with the text in argv. (2) The per-session settings file (`--settings`), as for `outputStyle`. (3) An env var.
**Why:** `lib/spawn-utils.js` `quoteForCmd` refuses `%` and mangles quotes on a Windows `.cmd` shim, which free text will hit. The `--settings` file has no known system-prompt key, so using it would invent a CLI feature; an env var for a 20 KB text hits size limits and is not a documented prompt input. Append is the default because replace drops the CLI's own tool guidance. Cost: unavailable on a CLI without the file flags; a stored replace prompt with only the append flag installed applies no prompt, silently (recorded as a known limit). UNVERIFIED on 2.1.246.

## [2026-10-29] Thinking off is the env var `MAX_THINKING_TOKENS=0` only
**Decision:** `thinkingOff` starts the session's CLI process with `MAX_THINKING_TOKENS=0` (`session-env.js`); no flag and no `set_max_thinking_tokens` control request. It applies from the next message through the idle restart.

## [2026-10-29] Rewind: the cut point is the last assistant uuid before the message; the restart is transactional; no `--fork-session`
**Decision:** `afterUuid` = the last top-level assistant uuid before the message (`null` for the first message: a fresh CLI conversation, no unknown flag). Otherwise restart with `--resume <id> --resume-session-at <afterUuid>` and wait for `initialize`; on failure restore the old id, items and `resumeAt`. `resumeAt` stays until the next message's replay. The removed tail is not kept in the GUI.
**Alternatives considered:** Seeding a new conversation with the earlier history as text (lossy, costs tokens). `--fork-session` (new session id, loses the link to the GUI session). Keeping the cut tail for an undo (more state, more UI; Desktop removes it). Gating the flag on `--help` (it is probably hidden, so the check would always fail).
**Why:** `--resume-session-at` keeps messages up to and including the given one, so the cut point has to be the message before. A hidden flag cannot be detected, so the restart is tried and rolled back. Keeping `resumeAt` until the next replay is needed because the cut lives only in memory until a new message is written; clearing it earlier would let an idle restart bring the removed turns back. A stopped or crashed turn has no final assistant uuid, so the cut can land one answer earlier than the GUI shows (documented limit).

## [2026-10-29] Rewind: files first, then the conversation; the cut is validated before anything changes; the CLI writes the files
**Decision:** The order is validate the cut (`requireCutPoint`, for any mode touching the conversation), restore files (`rewind_files` on the live process, after a dry-run preview), then restart the conversation. A failed file step changes nothing; a failed restart after restored files says so ("הקבצים כבר הוחזרו."). The GUI writes no files itself.

**Why:** The current process holds the full checkpoint history, and file restore is the step most likely to be unsupported or to fail, so it goes first and fails alone. Using the CLI's own checkpoints keeps path rules and write safety in one place and works outside git.

## [2026-10-29] Fallback model: strict whitelist, equal-to-main refusal, flag left out when unsupported

## [2026-10-27] A save is checked by content hash and written in place
**Decision:** Opening returns a sha256 of the raw bytes; `PUT` sends it back as `baseHash`; a mismatch is HTTP 412 and only `overwrite === true` forces. The file is written in place, in one synchronous block with the re-read and the compare.
**Alternatives considered:** (1) Compare modification time. (2) Write a temp file and rename it over the original. (3) Lock the file.
**Why:** Modification time is unreliable on Windows and network drives and changes without a content change. Temp-plus-rename is atomic but fails on Windows when another program holds the file, drops the file's mode and breaks hard links; VS Code writes in place by default. A synchronous block leaves no race inside the server. The cost, accepted: a crash mid-write can truncate the file, and a hard link planted in the folder is written through. Two Stage 3 fixes: `overwrite` must be exactly `true`, and the answer's hash belongs to the text that was sent, not a draft typed afterwards.

## [2026-10-27] Writes refuse `.git`, the GUI's own data and config; mixed line endings and non-UTF-8 files are not edited
**Decision:** The save route refuses any `.git` segment, the server's `data/` folder (`DATA_DIR`), `config.json` (`CONFIG_PATH`), uploads, `..`, NUL, non-regular files and, on win32, a `:` in the name. **Alternatives considered:** (1) Allow everything the viewer can read. (2) Normalize mixed endings to the dominant one on save. (3) Decode other encodings.
**Why:** A file in `.git/hooks` is code that runs on the next git command, and `data/` or `config.json` would let a page overwrite the GUI's own state and token settings. Normalizing mixed endings would rewrite every line (a huge diff in the Changes pane) without telling the user; refusing to save is safe. Re-encoding could corrupt the file. Known gap: a hard link inside the folder to a protected file bypasses the check.

## [2026-10-27] Shell commands run as a fresh shell per command, not a persistent shell
**Decision:** The Terminal pane and `!` commands spawn one shell per command (`lib/terminal/shell-run.js`), stdin closed, output streamed over SSE. `cd`, environment and shell state do not carry between commands.
**Alternatives considered:** (1) A persistent shell over pipes, with a sentinel to find the end of each command. (2) node-pty (a dependency, native build). (3) PowerShell only, or cmd only.
**Why:** No new npm dependencies is a platform rule, so no PTY. cmd.exe and PowerShell over plain pipes show no prompt and give no reliable end-of-command signal, interactive programs hang, and exit codes and output of consecutive commands get mixed. A spawn per command gives an exact exit code, a clean kill of the process tree and output tied to one command, which `!` needs for Claude's context. The cost, accepted and told to the user: no persistent `cd` or variables, no interactive programs, no colours (ANSI stripped), no TUI. Windows behaviour (cmd with `chcp 65001`, PowerShell `-EncodedCommand`, `taskkill /T /F`, UTF-8 output) was written but never run on Windows.

## [2026-10-27] `!` output reaches Claude as a prefix of the next message; the pane's commands do not

## [2026-10-27] Shell routes are POST-only and refuse archived sessions without restoring them

## [2026-10-27] A turn with corrections still waiting is held open; fallback after 20 s; corrections need `--replay-user-messages`
**Decision:** The runtime (`lib/runtime-corrections.js`) tracks the uuids it sent. A replay event with that uuid marks one taken in. When a successful `result` arrives while some still wait, the CLI will run another turn for them, so the GUI keeps the turn open (`turnActive` stays true; no turn-end hook, no notification, no `dispatchNext`). If no assistant, stream or replay event arrives within 20 s (`HOLD_MS`) the tracking is cleared and the turn ends; if a turn then starts anyway the session is set running again (`onTurnResume`). The flag `--replay-user-messages` is added only when `--help` lists it; without it Enter falls back to the queue, since nobody could tell when a correction was taken in. Stop cancels the waiting uuids with `cancel_async_message` and names the lost corrections in a notice.
**Alternatives considered:** (1) End the turn at the first result and let the next turn arrive as an unannounced run. (2) A 5 s fallback (my Stage 1 estimate). (3) Rely on the CLI's interrupt to sweep unconsumed messages. (4) Match corrections by order or count if the uuid does not come back.
**Why:** Ending at the first result would fire the notification, the idle timer, model-health and the GUI queue in the middle of a conversation the CLI is still having. The fallback is 20 s in the build (my Stage 1 estimate was 5 s; the local model can be slow, which is the likely reason); a next turn that comes later is handled by `onTurnResume`. `cancel_async_message` makes Stop deterministic instead of trusting an unverified sweep. The cost: if the real CLI does not return the uuid, every turn that got a correction ends 20 s late, and a stop exactly during a hold with no next turn ends only through the 6 s kill timer. All of this was simulated with the fake CLI; the real 2.1.246 is unverified.

## [2026-10-27] Worktree names and removal are conservative: `-b`, a unique name, no `--force`, the branch stays
**Decision:** The branch is created with `-b` (never `-B`) after the name was checked free as a folder and as a branch; deleting a session asks a second question, "להסיר גם את ה-worktree?", and removal uses `git worktree remove` without `--force` (uncommitted changes keep the folder, with a toast naming the path); the user's actions never delete a branch. The removal target is the path stored on the session, verified under `<root>/.claude/worktrees` and listed by git. A fork shares the worktree, so the question is skipped and the folder kept while another session uses it.
**Alternatives considered:** (1) `-B`, as the CLI does. (2) Always remove the worktree with the session (from memory, Desktop removes it on archive; this was unverified when written and was confirmed from the Desktop docs page in D6, see the first entry above), or never. (3) `--force` after a confirmation. (4) Delete the branch too when it has no unique commits.
**Why:** `-B` resets an existing branch, so a branch kept after an earlier removal could silently lose its commits; `-b` with a checked name makes that impossible. A branch holds the work, a worktree folder is a copy, so only the folder is ever offered for removal, and git's own refusal on uncommitted changes is the safety net, so no force. ## [2026-10-27] The Changes pane has its own route; untracked files are synthesized in node
**Decision:** `GET /api/sessions/:id/diff` (lib/git/session-diff.js) returns one text: `git diff` against HEAD for the whole repository, followed by every untracked file (`git ls-files --others --exclude-standard`) written as a "new file" diff that adds all its lines. The new-file diffs are built in node with limits: at most 100 files, 512 KB each, 2 MB read per request, `lstat` so symlinks are skipped, binary (NUL in the first 8 KB) and empty files handled; skipped files are counted (`newFilesSkipped`).
**Alternatives considered:** (1) Reuse `/api/git` (`gitChanges`) as it is. (2) `git diff --no-index -- /dev/null <file>` for each untracked file. (3) `git add -N` (intent to add) so git itself lists them. (4) Show untracked files by name only, with no diff (descope).
**Why:** `gitChanges` has no untracked files, and Claude often creates new files, so a pane without them would miss part of what a reviewer wants to comment on (the rail already counts them as files). `git add -N` changes the user's index, which a read-only view must never do. A name without lines allows no line comments. `--no-index` was the closest alternative: it needs one git process per file, and its exit code 1 means "differences found", which the shared `git()` helper reports as a failure. Building the text in node keeps the limits (count, size, symlinks, binary) in one place and produces the same format the one parser (`diff-parse.js`) already reads. The cost: the synthesized text is not byte-identical to git's (mode always `100644`, no "\ No newline at end of file" line, a non-UTF-8 file is decoded as UTF-8), and the route reads file contents beyond the session folder (documented in ARCHITECTURE.md -> Security).

## [2026-10-27] The pane diffs the whole repository against HEAD; the /diff panel keeps staged and unstaged apart
**Decision:** The Changes pane shows each file once, as its net change from HEAD (staged and unstaged merged), for the whole repository from its top level. The settings-modal git panel (`/diff`, `/api/git`) is unchanged: staged then unstaged, so a file can appear twice there.
**Alternatives considered:** (1) The pane uses the same staged + unstaged text as `/diff`. (2) Only the session folder (a pathspec of `.`). (3) Switch `/diff` to the new route too.
**Why:** A comment is anchored by file path, side and line, so the same path appearing twice would make the anchor ambiguous; one diff per file is also the natural unit to review file by file. The whole repository, because the rail's counts already come from git commands without a path and a session started in a subfolder would otherwise hide changes the rail counts. Leaving `/diff` alone keeps an existing, tested screen as it was and was not part of this feature. The cost: the rail's counts (numstat; untracked files as files only) and the pane's toolbar counts (new files' lines included) can differ, and the pane reads more than the session folder.

## [2026-10-27] Line comments are anchored by path, side, line and text, and are never dropped silently
**Decision:** A comment keeps `{ path, side, line, quote }` (the line's text when written). It shows under its line only while the line still has the same number and text; otherwise it moves to "הערות על שורות שהשתנו מאז" under its file, or (file gone from the diff) to a list at the top. Such comments stay deletable and are still sent. Comments are cleared only after a successful send.
**Alternatives considered:** (1) Anchor by line number only. (2) Drop comments whose line changed at the refresh after a turn. (3) Clear all comments on every refresh.
**Why:** The pane refreshes when a turn ends, and Claude's edits shift line numbers, so a number-only anchor would put a comment on the wrong code, while dropping would lose what the user wrote before they sent it. Comparing the text as well keeps a comment on its line only when it is still about that line; the message sent to Claude quotes the line, so a moved comment still says what it was about. The cost: a comment on a line that was only reindented shows under "changed since" instead of in place.

## [2026-10-27] The pane area belongs to the main session only and is hidden by a room rule
**Decision:** The workspace panes and the session details rail are shown for the main (active) session only. The area appears only when the workspace row has at least 560 px for the chat plus the column's width; otherwise it is hidden, the saved choice is kept, and the toggle only shows a toast. There is no special case for the split view: it narrows the main region, so the same rule hides the area. Open panes and the width are global per browser, not per session.
**Alternatives considered:** (1) Panes for both the main and the split session. (2) Opening a pane closes the split view (or the reverse). (3) Per-session open panes. (4) A viewport media query instead of measuring the row.
**Why:** Desktop panes belong to the focused session, and `/btw` and the search bar are already main-only, so the user's mental model stays consistent. At the split view's 1000 px minimum the main region is about 360 px, so the chat would be squeezed under both a rail and a split pane; a rule on the real row width covers this and every other narrow case (collapsed or open sidebar, any window size) with one check and no coupling between the two features. Keeping the saved choice (and not changing it on a toggle without room) means a narrow window never loses the user's layout. The cost: on a very wide window the area can sit next to the split pane, which was judged acceptable. Ctrl+\ was left untouched on purpose (a pending question for D4); D4 answered it: see the entry "Ctrl+\ closes the focused pane" above.

## [2026-10-27] The rail's change totals come from a small `git-summary` route, not from `/api/git`
**Decision:** `GET /api/sessions/:id/git-summary` (lib/git/changes.js `gitSummary`) returns `{ isRepo, branch, files, untracked, added, removed }` from `git status --branch` plus `git diff --numstat` (staged + unstaged). It takes the folder from the session on the server and has no `cwd` parameter. The git runner and its safety flags moved to lib/git/run.js so both git views share them.
**Alternatives considered:** (1) Reuse `/api/git` and count `+`/`-` lines of the returned diff in the browser. (2) Add the summary to `lib/workspace-info.js`. (3) Count what Claude's edit tools wrote (as the per-turn card does) instead of asking git. (4) Count the lines of untracked files.
**Why:** `/api/git` returns up to 300000 characters of diff and cuts it, so counts from it would be wrong for big changes and heavy to fetch on every turn; numstat gives exact totals in a few bytes. `workspace-info.js` was already at the size budget and git is a separate topic (one folder per feature), and moving the runner keeps the safety flags in one file. Asking git covers Bash-made changes that the edit-tool view misses, at the price that the card shows the folder's uncommitted changes, including ones not made in this session (said in its tooltip and the spec). Untracked files are counted as files, not lines, because reading every new file would be unbounded work for a card that refreshes on each turn.

## [2026-10-27] The file viewer reads the file's current text through a session-scoped route
**Decision:** `GET /api/file-view?sessionId=&path=` (lib/file-view.js) returns the file as it is now. The allowed roots (session folder, `addDirs`, uploads) are taken from the session on the server, compared as real paths, and any `cwd` parameter is ignored.
**Alternatives considered:** (1) Show the content recorded in the tool item (Read result, Edit strings) with no new route. (2) A route taking `cwd=` or any absolute path. (3) A general "read any file" route.
**Why:** The recorded tool content is partial (Edit holds only the changed strings, Read results may be cut) and cannot show surrounding lines or highlight a line range. A request-supplied `cwd` or free path would make the folder check meaningless and turn the route into an arbitrary-file reader, which the no-auth, cross-site-GET issues make worse. Session-scoped roots limit it to the places Claude already works in without asking. The cost is that the view can differ from what the tool saw if the file changed since; marks are then simply omitted.

## [2026-10-27] Prompt templates are stored on the server, not in localStorage
_Superseded on 2026-10-30 (storage, ids and route shape): templates are now CLI custom command files, see the first entry. The reason to keep them on the server rather than in localStorage still holds._
**Decision:** Templates live in `data/templates.json` (lib/templates.js) behind `GET /api/templates`, `PUT/DELETE /api/templates/:id`; the browser generates the id and PUT upserts.
**Alternatives considered:** Per-browser localStorage (like the notification and sidebar-grouping preferences).
**Why:** Templates are user content worth keeping, not a display preference. The server file survives a browser reset or cleared site data and every tab sees the same list. The cost is a new route set and a data file, kept small by limits (name 80, text 20000, 200 templates) and an atomic write like the session store.

## [2026-10-27] /btw gets its own route, not the generic control whitelist
**Decision:** `POST /api/sessions/:id/side-question` (lib/side-questions.js) sends the `side_question` control request with a 10 minute timeout.
**Alternatives considered:** Add `side_question` to `WRITE_SUBTYPES` in lib/catalog-service.js and use the generic `/control` route.
**Why:** The generic control routes are documented as costing no tokens and have short default timeouts; `side_question` calls the model and the local model can be slow. A separate route keeps that guarantee true and allows input limits (question 4000 characters, history 20).

## [2026-10-27] Session search runs in the browser, no server index
**Decision:** Full-text search scans `session.items` in the browser (public/js/session-search.js), newest 3000 items per session, count capped at 99.
**Alternatives considered:** A server-side search endpoint or index over `data/sessions.json`.
**Why:** `/api/state` and SSE already give the browser every item, so no new route, no index to keep in sync with live streaming, and results stay current as items arrive. The cost is a scan per query, bounded by the cap and a 150 ms debounce.

## [2026-10-27] The split-view pane has a mini composer, and extras stay main-only
**Decision:** The second pane has a live thread, its approval cards and a compact composer (text, send, stop). Attachments, slash menus, `@`, chips and `/btw` stay in the main composer; a swap button makes the pane's session the main one.
**Alternatives considered:** A read-only second pane; a full second composer with every feature.
**Why:** The use case (one session plans, another executes) needs sending to both, so read-only is not enough. A full second composer would duplicate menus, attachments and commands that are wired to the single active session, for little gain; one-click swap covers them.
